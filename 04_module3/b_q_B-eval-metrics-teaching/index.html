평가지표 사전

모델의 답을 어떻게 점수로 바꾸는가 — 여섯 개의 자(尺)와 고르는 법

티처팀 발표 · 파트 A · B · C

PART A · 발표자 A

점수는 결과 전에 정한다

대전제 — 왜 지표가 여러 개인가

시험지에는 답보다 문항·배점·채점 기준이 먼저 놓인다. 평가도 마음에 드는 결과를 고르는 게 아니라, 무엇을 어떤 근거로 통과시킬지 결과 전에 정하는 일이다.

평가지표 = 모델 답의 어느 성질을 숫자로 바꿀지 정한 자(尺).

  • 자 하나가 길이·무게·온도를 다 못 재듯, 한 점수가 사실성·형식·유용성·안전성을 함께 뜻하지 않는다.
  • 먼저 성공을 문장으로 쓰고, 그 문장을 가장 적게 왜곡하는 지표를 고른다.
  • 같은 입력·같은 조건·같은 판정규칙을 고정 안 하면, 숫자 차이는 지시 효과가 아니라 조건 차이일 수 있다.
💡 학생팀에 꼭 남길 것
지표는 자(尺)다. 하나로 다 못 잰다 → 성공을 먼저 문장으로 쓰고 그에 맞는 자를 고른다. 조건 고정 없으면 숫자 비교 무의미.
🎤 발표 대본
"시험 볼 때 답안지보다 채점기준이 먼저 나오죠? 평가도 똑같습니다. 결과를 보고 고르는 게 아니라, 뭘 통과시킬지 미리 정하는 겁니다. 평가지표는 자예요. 그런데 자 하나로 길이·무게·온도를 다 못 재잖아요? 점수 하나도 사실이냐·형식이냐·안전하냐를 동시에 못 답합니다. 그래서 자가 여러 개고, 오늘 그 자들을 하나씩 봅니다."
PART A · 발표자 A

이진 판정 · exact match

규칙으로 딱 떨어지는 채점 ①

이진 판정 = 조건 지키면 1, 아니면 0 (결정적 채점).
exact match(정확 일치) = 출력이 기준 답(golden answer)과 정확히 같을 때만 통과.

  • 잘 맞는 곳: 선택지 분류, 고정 레이블, 짧고 유일한 추출 답, 정형 JSON
  • 장점: 값싸고, 누구나 같은 답을 같은 결과로 판정
💡 학생팀에 꼭 남길 것
기준 답과 글자까지 같아야 1점. 함정 — 표현만 다른 옳은 자유답을 0점으로 만들고, 사실성 자체는 못 잰다.
🎤 발표 대본
"제일 단순한 자입니다. 정답이랑 똑같으면 1, 아니면 0. 객관식이나 딱 정해진 답에 좋아요. 근데 함정이 있어요 — 뜻은 맞는데 표현만 다른 답도 무조건 0점이 됩니다. 그리고 '맞는 말인지'는 아예 못 봐요. 형식만 봐요."
PART A · 발표자 A

F1 — 정밀도와 재현율

규칙으로 딱 떨어지는 채점 ② (계산)

여러 항목을 뽑는 과업(예: 문서에서 기관명 추출)의 자. 실제 12개 중 모델이 10개를 뽑아 8개 맞음.

지표계산무엇을 보나
정밀도 Precision8/10 = 0.80뽑은 것 중 맞은 비율 → 오탐 위험
재현율 Recall8/12 ≈ 0.67실제 중 찾은 비율 → 누락 위험
F12×(.80×.67)/(.80+.67) ≈ 0.73둘의 조화평균

조화평균은 작은 쪽에 민감. P=1.0·R=0.0이면 산술평균은 0.5지만 F1 = 0.0.

💡 학생팀에 꼭 남길 것
정밀도=오탐, 재현율=누락. F1=조화평균(작은 쪽에 민감). 암 진단은 재현율 먼저, 스팸차단은 정밀도 먼저 — F1 하나로 어느 피해가 큰지는 못 정한다.
🎤 발표 대본
"여러 개를 찾는 문제예요. 정밀도는 '내가 뽑은 것 중 맞은 비율' — 엉뚱한 거 넣으면 떨어져요. 재현율은 '실제 있는 것 중 찾은 비율' — 빠뜨리면 떨어져요. F1은 둘을 합치는데, 산술평균 말고 조화평균이라 한쪽이 0이면 F1도 0이에요. 암 진단은 놓치면 안 되니 재현율, 스팸은 정상메일 막으면 안 되니 정밀도를 먼저 봅니다."
PART B · 발표자 B

BLEU — 번역의 자

모범답안과 비교하는 지표 ① (번역)

BLEU = 후보 번역과 참조 답(사람이 만든 모범 번역)의 n-gram 중첩을 주로 정밀도 관점으로 세는 지표.

  • n-gram = 연속한 n개 토큰 조각. → "모범 번역의 단어 조각을 내 번역이 얼마나 정확히 빌려왔나"
  • 참조 번역이 있고 표면 겹침이 유용할 때 보조 지표로 (짧은 답 벌점 있음)
💡 학생팀에 꼭 남길 것
BLEU = 번역용 · 정밀도 관점 · n-gram 겹침. 함정 — 좋은 번역도 어순·동의어 다르면 낮게, 겹쳐도 부정어 하나 바뀌면 뜻이 틀림. 사람 평가 대체 아님.
🎤 발표 대본
"BLEU는 번역 채점용이에요. 모범 번역이랑 내 번역이 단어 조각을 얼마나 똑같이 겹치나 봅니다. 근데 함정 — '고양이가 매트에 앉았다'랑 '매트 위에 고양이가 앉아 있었다'는 뜻은 같은데 순서가 달라서 점수가 낮게 나와요. 반대로 조각이 많이 겹쳐도 '안' 한 글자 바뀌면 뜻은 정반대죠. 표면만 보는 자입니다."
PART B · 발표자 B

ROUGE — 요약의 자

모범답안과 비교하는 지표 ② (요약)

ROUGE = 참조 요약에 든 n-gram 중 후보 요약이 포착한 비율을 특히 재현율 관점으로 보는 지표 묶음.

  • → "모범 요약의 핵심 조각을 내 요약이 얼마나 안 빠뜨렸나"
  • 문서·회의 요약처럼 참조 요약이 있는 과업에 사용 (ROUGE-N·ROUGE-L)
💡 학생팀에 꼭 남길 것
ROUGE = 요약용 · 재현율 관점 · 핵심 조각을 안 빠뜨렸나. 함정 — 길게 쓰면 재현율이 부풀고, 동의어·바꿔쓰기·사실오류·어색함은 못 잡는다. 높은 ROUGE ≠ 좋은 요약.
🎤 발표 대본
"ROUGE는 요약 채점용이에요. 방향이 BLEU랑 반대예요 — '모범 요약의 핵심을 내가 얼마나 안 빠뜨렸나'를 봅니다. 그래서 재현율 관점이죠. 함정 — 길게 막 쓰면 핵심이 우연히 많이 걸려서 점수가 올라가요. 근데 사실이 틀렸거나 문장이 어색한 건 못 봅니다."
PART B · 발표자 B · ★대조

BLEU vs ROUGE — 헷갈리지 않기

이 슬라이드 하나로 정리

BLEU

  • 과업: 번역
  • 관점: 정밀도
  • 질문: "얼마나 정확히 빌려왔나"
  • 벌점: 짧은 답 벌점

ROUGE

  • 과업: 요약
  • 관점: 재현율
  • 질문: "얼마나 안 빠뜨렸나"
  • 주의: 길게 쓰면 부풀려짐
💡 공통 — 둘 다 똑같은 한계
BLEU도 ROUGE도 표면 n-gram 중첩 신호일 뿐, 의미·사실의 증명이 아니다. 반드시 사람 표본 검토와 결합한다.
🎤 발표 대본
"이 한 장만 기억하세요. BLEU는 번역·정밀도·'정확히 빌렸나', ROUGE는 요약·재현율·'안 빠뜨렸나'. 이름 헷갈리면 B는 번역, R은... 요약이라고 외우세요. 그리고 둘 다 공통 약점 — 단어 겹침만 보지 뜻이 맞는지는 몰라요. 그래서 사람이 표본 검토를 같이 해야 합니다."
PART B · 발표자 B

perplexity (PPL)

모델의 내부 확신을 보는 온도계

PPL = 언어모델이 실제 다음 토큰에 준 확률을 지수화한 내부 확률 지표. 낮을수록 다음 말을 덜 놀라워한다.

  • → 문장을 한 토큰씩 가렸을 때 얼마나 확신 있게 예상하나 보는 온도계
  • 쓰임: 같은 모델·같은 토크나이저·같은 코퍼스에서 언어모델링 적합도·학습 변화 비교
💡 학생팀에 꼭 남길 것
함정 — 낮다 ≠ 맞다. 확신하는 답이 옳은 답은 아니다(유창하게 틀림). 토크나이저·문맥창이 값을 바꿔 다른 모델끼리 못 비교. 프롬프트 품질 비교엔 부적합 → 대신 "근거 없는 날짜 금지·확인 질문 여부"로 과업 성공을 직접 판정.
🎤 발표 대본
"PPL은 모델이 다음 단어를 얼마나 자신 있게 맞히나 보는 온도계예요. 낮으면 자신 있다는 뜻이죠. 근데 제일 큰 함정 — 자신 있는 게 맞는 건 아니에요. 틀린 배송일도 아주 유창하고 자신 있게 써요. 그래서 '이 프롬프트가 더 좋냐'를 PPL로 비교하면 안 됩니다. 대신 '없는 날짜 지어내지 마' 같은 걸 직접 채점해야 해요."
PART C · 발표자 C

pass@k — 실행으로 잰다

코드는 말이 아니라 실행 결과로 (계산)

pass@k = 한 코딩 문제에서 독립 후보 k개 중 적어도 하나가 단위 테스트를 통과할 확률(또는 추정치).

  • 코드·SQL처럼 실행해 검증 가능하고 여러 후보를 받을 수 있는 과업
  • 예: 후보 10개 중 3개 통과 → pass@1 추정 = 3/10 = 0.3
  • 통과 = 실제 실행 결과. 컴파일 오류·예외·틀린 반환값은 모두 실패
💡 학생팀에 꼭 남길 것
후보 k개 중 하나라도 테스트 통과. 함정 — k 커지면 점수 오름 → pass@1과 pass@100은 같은 성능 아님. temperature·후보수·테스트범위를 함께 적어야 재현. 후보 다양성도 성능의 일부.
🎤 발표 대본
"코드는 말로 '됐습니다' 하면 안 되고 돌려봐야 알죠. pass@k는 답안 k개 중 하나라도 테스트를 통과하면 성공으로 봐요. 10개 중 3개 통과면 pass@1은 0.3. 근데 k를 키우면 당연히 확률이 오르니까, pass@1이랑 pass@100을 같은 실력이라고 비교하면 안 돼요. 몇 개 후보로 쟀는지 꼭 같이 적어야 합니다."
PART C · 발표자 C

LLM-as-judge · rubric

정답이 하나로 안 닫히는 열린 품질

참조 답이 없고 유용성·설득력·안전성처럼 규칙 하나로 닫히지 않는 품질은 어떻게 잴까?

  • 구체 rubric(채점표)을 만들고 심사 모델(LLM)이 그 기준으로 채점
  • 반드시 사람 표본 검토를 함께
💡 학생팀에 꼭 남길 것
참조 답 없는 열린 품질 → rubric 기반 LLM-as-judge + 사람 검토 병행. 가장 유연하지만 가장 비싸고, 심사 모델도 편향될 수 있어 사람이 표본을 봐야 한다.
🎤 발표 대본
"'이 답이 설득력 있나, 안전한가' 같은 건 정답표가 없죠. 이럴 땐 채점 기준표를 만들고 AI한테 채점을 시켜요. 이게 LLM-as-judge입니다. 근데 채점하는 AI도 순서에 휘둘리거나 편향될 수 있어서, 사람이 일부는 직접 봐야 해요."

💡 학생팀에 꼭 남길 것

🎤 발표 대본
"정리하면, 자를 고르는 순서가 있어요. 첫째, 자동으로 채점되나? 되면 그게 제일 싸요. 안 되면 둘째, 모범답안이랑 비교하나? 정답 하나면 exact match, 여러 개면 F1, 번역이면 BLEU, 요약이면 ROUGE. 그것도 아니면 셋째, 사람 판단이 필요한 거라 rubric으로 AI 심사 + 사람 검토. 이 순서가 곧 돈 순서예요. 싼 것부터 쓰고 꼭 필요한 데만 비싼 걸 씁니다."
마무리 · 한 문장으로
