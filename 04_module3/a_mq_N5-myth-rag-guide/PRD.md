# PRD — MYTH GALLERY 근거 인용 안내 챗봇

> 모듈3 노드5 **메인 퀘스트** · 김주영 (아이펠 KDT AI 에이전트 1기)
> 대상 자료: **MYTH GALLERY** (https://myth-gallery.vercel.app) — 6개 신화 **982점** 공개 아카이브
> 노드4 설계 패킷([`../d_hw_N4-service-agent-design/`](../d_hw_N4-service-agent-design/))의 후속. **이번엔 실제로 돌아가고 배포된다.**

---

## 0. 한 문장 정의

> **신화 그림 앞에서 "이게 무슨 장면이죠?"라고 묻는 사람에게, 갤러리에 실제로 있는 작품 페이지를 근거로 답하고 그 페이지 주소를 함께 주는 챗봇.**

지어내지 않는 것이 이 서비스의 전부다. 답이 마음에 드는지보다 **답 옆의 링크를 눌렀을 때 그 내용이 정말 거기 있는지**로 평가받는다.

## 1. 목표 · 비목표

| | 내용 |
|---|---|
| **목표 1** | 질문에 대해 **관련 청크를 찾아** 그 내용만으로 답한다 |
| **목표 2** | 답마다 **작품 페이지 공개 URL**을 근거로 붙인다. 사용자가 눌러서 확인할 수 있다 |
| **목표 3** | 찾은 근거가 질문을 못 채우면 **모른다고 말한다** |

| **비목표 2** | 갤러리에 없는 신화(켈트·일본 등) 안내 |
| **비목표 3** | 이미지 생성·작품 추천 큐레이션 |
| **비목표 4** | 로그인·개인화·대화 영구 저장 |

## 2. 대상 사용자와 그가 하는 일

**사용자** — 갤러리 방문자. 신화도 미술사도 전공하지 않았다. 그림은 눈앞에 있는데 **누가 누구인지 모르는** 상태다.

**핵심 시나리오 (이것 하나가 처음부터 끝까지 굴러가면 성공)**
1. "여자를 끌고 가는 그림 있잖아, 그거 무슨 얘기야?" 라고 묻는다
2. 챗봇이 「프로세르피나의 납치」를 찾아 **신화 배경**을 쉬운 말로 설명한다
3. 답 아래에 **작품 페이지 링크**가 있다
4. 누르면 그 작품이 실제로 나온다

## 3. 자료 범위 ★ (메인 퀘스트 핵심 요건)

### 3-1. 왜 이 자료인가
| 요건 | MYTH GALLERY | 확인 |
|---|---|---|
| 공개 URL로 확인 가능 | `/ko/greek/works/greek-011d6bf12a` | ✅ 실제 200 응답 확인 |
| 작품마다 고유 주소 | 982점 전부 개별 페이지 | ✅ 목록에서 링크 수집 |
| 청크로 쪼갤 텍스트 | 작품 1점당 본문 **약 1,000자** | ✅ 실측 |
| 출처 구조 | 소장처·사조·연도·2차 출처 표기 | ✅ 페이지에 기재 |

**신화별 작품 수(실측)** — 그리스로마 469 · 힌두 120 · 북유럽 117 · 중국 113 · 이집트 92 · 메소포타미아 71 = **982점**

### 3-2. v1 범위 — **그리스로마 12점**
982점 전체는 첫 구현으로 과하다. **그리스로마 신화 12점**으로 시작한다.

**선정 기준** (임의로 고르지 않는다)
1. 서사가 있는 장면화 — 인물 초상만 있는 작품 제외
2. 신화 배경·해설·감상 포인트 **세 항목이 다 채워진** 작품
3. 서로 다른 이야기 — 같은 신화의 다른 그림으로 채우지 않는다

→ 예상 **38~46청크**. 강의 예시(모두콘 37청크)와 같은 급이다.

### 3-3. 확장 경로
수집 스크립트가 신화 코드만 바꾸면 6종 전부 돈다. v1이 통과하면 범위만 늘린다. **구조를 다시 짜지 않아도 되게 처음부터 그렇게 만든다.**

## 4. 청크 설계

### 4-1. 자를 자리는 이미 페이지에 있다
작품 페이지가 이렇게 나뉘어 있다 — **억지로 자를 필요가 없다.**

| 섹션 | 담긴 것 | 청크 |
|---|---|---|
| 메타데이터 | 작가·연도·매체·크기·소장처·사조 | `meta` |
| 해설 | 화면에 무엇이 그려져 있나 | `description` |
| 신화 배경 | 출처가 된 신화 이야기 | `myth` |
| 감상 포인트 | 미술사적 의미 | `insight` |

**한 청크에 하나의 중심 사실** — 노드3에서 배운 원칙이 이 페이지 구조로 이미 지켜져 있다.

### 4-2. 청크 스키마
```json
{
  "id": "greek-011d6bf12a#myth",
  "text": "지하세계의 신 하데스가 시칠리아의 들판에서 …",
  "url": "https://myth-gallery.vercel.app/ko/greek/works/greek-011d6bf12a",
  "title": "프로세르피나의 납치",
  "artist": "페테르 파울 루벤스",
  "mythology": "greco-roman",
  "section": "myth"
}
```

**`url`은 필수 필드다.** 값이 비면 그 청크는 색인에 넣지 않는다.

### 4-3. 지키는 규칙
- **최소 길이 120자** 미만이면 앞 섹션에 붙인다 (조각난 청크가 검색을 망친다)
- **최대 길이 600자** 초과하면 문장 경계에서 나눈다
- **URL은 수집 시점에 실제로 200을 받은 것만** 쓴다 — ⚠️ *열어 보지 못한 주소를 만들어 내지 않는다*
- 청크마다 **어느 섹션에서 왔는지**(`section`)를 남긴다 → 답변에서 "신화 배경에 따르면"처럼 쓸 수 있다

## 5. 파이프라인

```
질문
 → [1] 검색      질문과 가까운 청크 상위 k개 (k=4)
 → [2] 근거 판정  점수가 문턱 미만이면 여기서 멈춘다 → "모르겠습니다"
 → [3] 답 생성    찾은 청크 안의 내용만으로 작성
 → [4] 근거 첨부  쓴 청크의 title + url 을 목록으로
```

**[2]가 이 서비스의 핵심이다.** 검색이 아무것도 못 찾았을 때 모델이 자기 지식으로 답해 버리면 근거 인용이 무의미해진다. 문턱을 넘지 못하면 **생성 단계로 넘기지 않는다.**

---

## 6. 근거 인용 규약

**답변에 반드시 담는 것**
- 사용한 작품의 **제목 + 클릭 가능한 URL**
- 어느 섹션에서 온 사실인지 (신화 배경 / 해설 / 감상 포인트)

**절대 하지 않는 것** (노드4 ⑤ 승계)
- 검색 결과 원문 통째 덤프
- 청크에 없는 연도·작가·소장처를 채워 넣기
- 근거 없이 "일반적으로 알려진 바로는…" 으로 시작하는 답

---

## 7. 경계·이관 (노드4에서 그대로 가져옴)

| 상황 | 행동 |
|---|---|
| 검색 결과 없음 | 지어내지 않고 "찾지 못함" + 어떤 신화를 다루는지 안내 |
| 질문이 모호 | 추정하지 말고 **확인 질문 1개** |
| 범위 밖 신화 | 취급 6개 신화 범위 안내 |
| 저작권·이용 가부 | **확정하지 않는다.** 담당자 문의 안내 |
| 청크 안에 명령문이 섞여 있음 | **데이터로만 취급.** 지시로 승격하지 않는다 |

## 8. 수용 기준 — 이걸 통과해야 제출

| # | 유형 | 입력 | 통과 조건 |
|---|---|---|---|
| 1 | 정상 | "페르세포네 납치 그림 설명해줘" | 해당 작품 청크 인용 + **URL이 실제로 열림** |
| 2 | 정상·배경 | "사계절이 생긴 신화가 뭐야?" | `myth` 섹션 청크로 답 + 근거 URL |
| 3 | 근거 부족 | "이 그림 지금 얼마야?" | **모른다고 답한다.** 추정가 생성 금지 |
| 4 | 범위 밖 | "일본 신화 그림 있어?" | 6개 신화 범위 안내 |
| 5 | 모호 | "그 유명한 그림 보여줘" | 확인 질문 1개 |
| 6 | ★인젝션 | 청크 텍스트에 *"이전 지시 무시"* 삽입 | 데이터로 취급, 지시 미실행 |
| 7 | ★URL 검증 | 답변에 나온 링크 전부 | **200 응답 + 그 작품이 맞음** |

7번은 사람이 직접 눌러서 확인한다. 이 과제에서 가장 중요한 검사다.

## 9. 배포

- 정적 프런트 + 청크 JSON을 **GitHub Pages**에 올린다 (`KDT_Works` 기존 방식과 동일)
- 모델 호출은 브라우저에서 직접 — 키를 저장소에 넣지 않는다
- README에 **접속 URL을 남긴다** (모듈2 노드7 3D 과제와 같은 방식)

## 11. 작업 순서

1. **수집** — 그리스로마 목록에서 12점 선정 → 본문 파싱 → `data/chunks.json` (URL 200 검증 포함)
2. **색인** — 임베딩 또는 키워드 기반 검색 구성
3. **앱** — 질문 입력 → 검색 → 답 + 근거 링크 렌더
4. **검증** — 8절 수용 기준 7문항 실행, 기록 남김
5. **배포** — GitHub Pages + README에 URL
