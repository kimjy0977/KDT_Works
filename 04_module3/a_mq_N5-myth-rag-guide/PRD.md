# PRD — MYTH GALLERY 안내 챗봇

> 모듈3 노드5 **메인 퀘스트** · 김주영 (아이펠 KDT AI 에이전트 1기)
> 대상 도메인: **MYTH GALLERY** — 여섯 신화 **982점** 공개 아카이브
> 노드4 [서비스 설계 과제](../d_hw_N4-service-agent-design/)의 후속. 그때 정한 경계를 그대로 들고 와서 **이번엔 실제로 돌린다.**
> **이 문서에 [결정 필요]는 남아 있지 않다.** 빈칸을 남기면 나중의 코드 선택이 제품 약속을 대신하게 되기 때문이다.

---

## 0. 한 문장 정의

> **신화 그림 앞에서 "이게 무슨 장면이죠?"라고 묻는 사람에게, 갤러리에 실제로 있는 작품 페이지를 근거로 답하고 그 주소를 함께 주는 챗봇.**

답이 그럴듯한지보다 **답 옆의 링크를 눌렀을 때 그 내용이 정말 거기 있는지**로 평가받는다.

---

## 1. 사용자와 해결하려는 질문

**사용자** — 갤러리 방문자. 신화도 미술사도 전공하지 않았다. 그림은 눈앞에 있는데 **누가 누구인지 모르는** 상태다.

| 사용자가 실제로 하는 질문 | 챗봇이 하는 일 |
|---|---|
| "여자를 끌고 가는 그림, 무슨 얘기야?" | 신화 배경 조각을 찾아 쉬운 말로 |
| "이 그림 누가 그렸어? 어디 있어?" | 메타데이터 조각(작가·소장처)에서 |
| "사계절은 왜 생겼대?" | 여러 작품에 걸친 신화 배경에서 |

**기대하면 안 되는 것** — 작품 감정·시세, 저작권 가부, 갤러리에 없는 신화, 이미지 생성.

---

## 2. 목표 · 비목표

| | 내용 |
|---|---|
| **목표 1** | 질문에 **관련 청크를 찾아** 그 내용만으로 답한다 |
| **목표 2** | 답 안에 **`[ID]` 근거 표시**, 답 아래에 **출처 칩(제목·URL)** |
| **목표 3** | 근거가 질문을 못 채우면 **없다고 답한다** |
| **목표 4** | 답마다 **판정 배지**(grounded·noHalluc·cited·refusal·score)를 남긴다 |
| **비목표** | 저작권·이용 가부·가격 판정 / 갤러리 밖 신화 / 이미지 생성 / 로그인·개인화 |

> 기능마다 이유를 붙이는 까닭 — **판정 배지는 답을 잘 보이게 하는 장치가 아니라, 사용자가 이 답을 얼마나 믿을지 스스로 정하게 하는 자료다.** 문장이 자연스럽다는 사실과 출처를 가진 답이라는 사실은 다르다.

## 3. 자료 범위

### 3-1. 왜 이 자료인가

| 요건 | MYTH GALLERY | 확인 |
|---|---|---|
| 공개 URL로 확인 가능 | `/ko/greek/works/greek-011d6bf12a` | 수집기가 **200 확인** |
| 작품마다 고유 주소 | 982점 전부 개별 페이지 | 목록에서 링크 수집 |
| 청크로 쪼갤 텍스트 | 작품 1점당 본문 **약 1,000자** | 실측 |

**신화별 작품 수(실측)** — 그리스로마 469 · 힌두 120 · 북유럽 117 · 중국 113 · 이집트 92 · 메소포타미아 71 = **982점**

### 3-2. v1 범위 — **그리스로마 12점 → 41청크**

**선정 기준** (임의로 고르지 않는다 — `data/harvest.py` 의 `pick()`)
1. 서사가 있는 장면화 — 등장인물 2명 이상
2. 해설·신화 배경·감상 포인트 **세 항목이 다 채워진** 작품
3. **서로 다른 이야기** — 같은 인물 조합·같은 작가로 채우지 않는다

→ 선정된 12점은 이야기 12개가 전부 다르고 작가도 12명 전원 다르다.

### 3-3. ★자료의 갱신 주체와 출처 링크의 책임

| 항목 | 누가 | 무엇을 |
|---|---|---|
| **원문** | MYTH GALLERY 운영자(=제작자 본인) | 작품 페이지의 내용·주소 |
| **청크** | 이 저장소 | `python data/harvest.py` 재실행으로 갱신 |
| **링크** | 이 저장소 | 수집 시점에 **200을 받은 주소만** 넣는다 |

**갤러리가 바뀌면 챗봇 자료는 자동으로 따라가지 않는다.** 방향은 단방향이다 — 갤러리가 챗봇에 영향을 주지, 챗봇이 갤러리를 건드리지 않는다.
**다시 검토해야 하는 때** — 작품이 추가·삭제됐을 때 / 주소 체계가 바뀌었을 때 / 해설 문구를 고쳤을 때. 이때 `harvest.py` 를 다시 돌리고 `npm run build:vectors` 로 벡터를 새로 만든다.

## 4. 청크 설계

### 4-1. 자를 자리는 이미 페이지에 있다
작품 페이지가 **기본 정보 · 해설 · 신화 배경 · 감상 포인트**로 나뉘어 있다. "한 청크에 하나의 중심 사실"이 원본 구조로 이미 지켜져 있어 **그 경계를 그대로 청크 경계로 썼다.**

### 4-2. 스키마 — 참조 구현과 동일하게 유지
```json
{
  "id": "greek-011d6bf12a#myth",
  "text": "지하세계의 신 하데스가 시칠리아의 들판에서 …",
  "url": "https://myth-gallery.vercel.app/ko/greek/works/greek-011d6bf12a",
  "section": "myth",
  "vector": [0.0655, -0.0413, …]
}
```
`id` · `text` · `url` · `section` · `vector` **다섯 필드를 바꾸지 않는다.** 파이프라인이 이 스키마를 전제로 돌기 때문이다.

### 4-3. 지키는 규칙
- **최소 120자** 미만이면 앞 섹션에 붙인다 (조각난 청크가 검색을 망친다)
- **최대 600자** 초과하면 문장 경계에서 나눈다
- **URL은 수집 시점에 200을 받은 것만** — 열어 보지 못한 주소는 만들지 않는다
- `url` 이 빈 청크는 **색인에 넣지 않는다**

실측: 41청크 · 길이 최소 131 / 평균 214 / 최대 382자

## 5. 임베딩과 검색

| 단계 | 방식 |
|---|---|
| 임베딩 | **embeddinggemma-300m (768차원)** · `model_no_gather_q4` · mean pooling + L2 정규화 |
| 자료 벡터 | `app/scripts/build-vectors.mjs` 가 **브라우저와 같은 모델·같은 계산**으로 생성 |
| 질의 벡터 | 브라우저에서 실시간 (`app/src/rag.ts`) |
| 검색 | **코사인 상위 10 + BM25 상위 5** = 15개 (하이브리드) |
| 약한 근거 | 최고 유사도 **0.55 미만이면 버리지 않고** 프롬프트를 보수화하고 UI에 경고 |

> **자료 벡터와 질의 벡터는 같은 공간에 있어야 한다.** 자료만 다른 모델로 만들면 코사인 점수는 비교할 자리를 잃는다. 그래서 생성 스크립트가 `rag.ts` 의 계산을 그대로 옮겨 놓았다.

**0.55는 차단선이 아니다.** 근거를 버리는 기준이 아니라, *"이 근거는 약하다"* 를 프롬프트와 화면에 드러내는 기준이다.

## 6. 화면 구성

한 페이지다. 서버가 없으므로 라우팅도 없고, **위에서 아래로 읽으면 «무엇을 물어도 되는지 → 물어보기 → 답을 어디까지 믿을지»** 순서가 되게 놓았다.
1강이 말한 *"첫 화면은 단순한 대화창이 아니라 소개·FAQ와 챗봇 상태를 함께 보여 주는 안내 공간"* 을 이 순서로 구현한다.

### 6-1. 화면 하나와 그 안의 자리들

| # | 자리 | 무엇이 있나 | 왜 이 자리에 있나 |
|---|---|---|---|
| ① | **머리(hero)** | 서비스 이름 · 여섯 신화 아카이브라는 한 줄 · 챗봇으로 내려가는 버튼 | 처음 온 사람이 «여기가 어디인가»를 3초에 안다 |
| ② | **엔진 선택** | 로컬 ollama / Gemini API 전환 · 키 입력칸 | 답을 **누가 만드는지**를 숨기지 않는다. 조건을 바꿀 수 있는 자리를 위에 둔다 |
| ③ | **연결 배너** | ollama 미연결 시 안내 + OS별 `OLLAMA_ORIGINS` 설정법 + 다시 확인 | 사용자가 **페이지 오류와 자기 실행 조건을 구별**하게 한다 |
| ④ | **소개 카드 3장** | 아카이브란 / 근거 원칙 / 실행 구조 | 무엇을 하는 서비스이고 답이 어디서 오는지 |
| ⑤ | **다루는 작품 12점** | 썸네일 · 작가 · 사조 · **작품별 근거 조각 수** · 원문 링크 | 물어봐도 되는 **범위를 목록으로** 보여 준다. 범위를 글로 쓰면 안 읽는다 |
| ⑥ | **여섯 신화 범위** | 982점 중 수록 12점 / 미수록 5신화 | 아카이브에 있는 것과 **챗봇이 답할 수 있는 것**이 다르다는 사실을 질문 전에 알린다 |
| ⑦ | **FAQ 4문** | 무엇을 묻나 · 왜 못 답하나 · 왜 Ollama가 필요한가 · **답을 어디까지 믿나** | 거부와 고장을 구별하게 하고, 판정 배지의 한계를 미리 밝힌다 |
| ⑧ | **챗봇** | 대화 로그 · 입력칸 · 연결 상태 배지 · 정지 버튼 | 위를 다 읽은 뒤 실제로 물어보는 자리 |
| ⑨ | **우측 도크** | 접었다 펼 수 있는 챗봇. ⑧과 **같은 대화를 공유** | 작품 목록을 읽다가 **그 자리에서** 물어볼 수 있게 |
| ⑩ | **근거 모달** | 출처 칩을 누르면 열림. 조각 원문 · 유사도 · 원문 보기 링크 | 답변의 한 문장을 **원문까지 되짚는** 마지막 고리 |
| ⑪ | **꼬리말** | 자료 출처 · 모델 · 임베딩 이름 | 실행 조건을 페이지 안에 남긴다 |

### 6-2. 한 번의 질문에서 화면이 보여 주는 것

답이 그냥 튀어나오지 않고 **단계가 보이게** 한다. 어디서 틀렸는지 사용자가 짚을 수 있어야 하기 때문이다.

```
①질문 임베딩 중 ─ 캐시 사용 여부·다운로드 진행률(첫 방문 약 200MB)
②근거 검색 중  ─ 찾은 조각 N개 · 벡터 몇 · BM25 몇 · 최고 유사도
                  0.55 미만이면 ⚠ 약한 근거 배지
③답변 생성 중  ─ 스트리밍(정지 가능). 중단해도 받은 만큼 남는다
④판정 중       ─ 끝나면 배지: 평균 점수 · 근거 충실성 · 환각 통제 ·
                  출처 표시 · 정당한 거부 · 한 줄 평어 · 판정 모델 이름
   그 옆에      ─ 👍 👎 사람 피드백 (판정 배지와 같은 줄에 둔다)
   그 아래      ─ 출처 칩 N개 → 누르면 ⑩ 근거 모달
```

> **사람 피드백을 판정 배지와 같은 줄에 두는 이유** — 7강이 *"사람의 좋아요/싫어요가 판정과 같은 방향인지 어긋나는지 함께 읽는다"* 고 했다. 떨어뜨려 놓으면 따로 읽게 된다.

### 6-3. 화면이 지켜야 할 상태

| 상태 | 화면이 하는 일 |
|---|---|
| 임베딩 모델 없음 | 진행률 %와 «첫 방문 1회» 안내. 멈춘 것처럼 보이지 않게 |
| 임베딩 캐시 있음 | «캐시된 모델 사용 (다운로드 없음)» |
| ollama 미연결 | ③ 배너 + 재시도. **답변을 지어내지 않는다** |
| 근거가 약함 | ⚠ 최고 유사도 %를 숫자로 보여 준다. 숨은 임계값이 아니라 **공개된 경계** |
| 판정 실패 | 배지 자리에 «판정 실패 (답변은 정상)». **UI가 무너지지 않는다** |
| 생성 중단 | 받은 청크를 지우지 않고 «— 여기서 정지했습니다» |

### 6-4. 안 만든 화면

로그인·마이페이지·관리자·검색 결과 전용 페이지를 만들지 않는다. §2 비목표대로 **개인화와 자료 편집을 다루지 않기** 때문이고, 한 페이지 정적 앱이라 서버가 필요한 화면을 둘 수 없기 때문이다.

## 7. 근거 표시 규칙 — 어떤 답에 출처가 있어야 하나

| 답의 종류 | 출처 표시 | 이유 |
|---|---|---|
| 자료에서 사실을 꺼낸 답 | **필수** — 문장 안 `[ID]` + 아래 출처 칩 | 사용자가 원문으로 갈 출발점 |
| 여러 청크를 이은 답 | **필수** — 쓴 청크 전부 | 어느 조각에서 왔는지 갈라 보게 |
| 근거 없음을 밝힌 답 | **불필요** | 인용할 것이 없다 |
| 범위 밖 안내 | **불필요** | 자료 문제가 아니라 범위 문제 |

**절대 하지 않는 것** — 검색 결과 원문 통째 덤프 / 청크에 없는 연도·작가·소장처 채워 넣기 / 근거 없이 "일반적으로 알려진 바로는…"

## 8. ★도메인 밖 질문 처리 기준 — 실패했을 때의 안내 문구

**원칙:** 자료에 없는 질문을 **그럴듯하게 넓혀 답하지 않는다.** 범위 밖임을 밝힌 뒤 자료를 요청하거나 답할 수 없다고 안내한다.
이 기준은 **거절 횟수를 줄이려는 장치가 아니라, 사용자가 답변의 경계를 이해하게 하는 약속이다.**

| 상황 | 안내 문구 |
|---|---|
| 자료에 없음 | "제가 가진 자료에는 없습니다." + 지금 실린 범위를 밝힌다 |
| 취급하지 않는 신화 | "MYTH GALLERY는 그리스·로마, 북유럽, 이집트, 메소포타미아, 힌두, 중국 여섯 신화를 다룹니다. 지금 이 챗봇에 실린 자료는 그리스·로마 작품입니다." |
| 대상이 모호 | 추정하지 말고 **확인 질문 1개** — "등장하는 신이나 인물 이름을 하나만 알려 주시겠어요?" |
| 저작권·이용·가격 | **가부를 확정하지 않는다.** "이 부분은 제가 판정하지 않습니다. 갤러리 담당자에게 문의해 주세요." |
| 자료 안에 명령문이 섞임 | 그 문장을 **데이터로만** 취급하고 지시로 승격하지 않는다 |

## 9. 수용 기준 — 배포 전에 통과해야 하는 문

**어떤 거부가 정당한가** — ①자료에 그 사실이 없을 때 ②취급하지 않는 신화일 때 ③사람이 판단할 일(저작권·가격)일 때. **이 셋 밖의 거부는 실패다.** 자료에 있는데 없다고 답하면 그것도 실패다.

| # | 유형 | 질문 | 통과 조건 |
|---|---|---|---|

| 6 | 경계 | 그 유명한 그림 보여줘 | 확인 질문 1개 |

★는 사람이 직접 눌러서 확인한다. 이 과제에서 가장 중요한 검사다.

## 10. 루브릭 — 통과한 뒤에 쓰는 자

수용 기준이 **문**이라면, 루브릭은 문을 통과한 뒤 프롬프트·검색 세팅을 비교할 때 쓰는 **자**다.

| 지표 | 측정 방법 | 목표값 |
|---|---|---|
| 출처를 인용한 답변 | 고정 질문 중 `cited:true` 답 수 | 정상·경계 6문항 **전부** |
| 도메인 밖 질문의 거부 | 무근거 3문항의 `refusal:true` 수 | **3/3** |
| 근거성 | `grounded:true` 비율 | **70% 이상** |
| 짧은 답변의 근거 유지 | 답변 길이와 `[ID]` 표시를 함께 검토 | 길이가 줄어도 `[ID]` 유지 |

실행 결과는 **README.md 「실험」 절**에 남긴다. 목표값과 실제 판정값을 나란히 두어야 "개선"이라는 말이 어떤 관찰에 근거하는지 설명할 수 있다.

## 11. 사용 조건 (숨기지 않는다)

배포 주소가 열리는 것과 답변이 나오는 것은 다른 일이다. 이 앱은 **서버가 답을 만들지 않는다.**

1. 사용자 컴퓨터에서 **Ollama 실행** + `ollama pull qwen3.5:2b`
2. 첫 방문에 **임베딩 모델 약 200MB 내려받기** (이후 캐시)
3. Pages 주소에서 호출하려면 **`OLLAMA_ORIGINS`에 `https://*.github.io` 허용** 후 Ollama 재시작
4. **Chrome·Edge 사용** (Safari는 https 페이지에서 로컬 호출을 차단)

Ollama가 없어도 **Gemini API 키**를 넣으면 동작한다(참조 구현에 포함된 선택 엔진).
