# CURATOR — 아카이브 등재 에이전트

> ## ★먼저 — 「등재」가 무엇을 하는지 정확히
>
> 이 서비스가 만드는 것은 **등재 레코드 JSON 한 건**입니다.
> **공개 아카이브에 «자동으로 써 넣지 않습니다».**
>
> | 이 서비스가 하는 것 | 사람이 하는 것 |
> |---|---|
> | 공개 데이터에서 **사실 수집** · **라이선스 판정** · **중복 확인** · 해설 초안 | 필드 확인·수정 → **승인** |
> | 승인 뒤 **레코드 JSON 확정** · 내려받기 | 내려받은 JSON 을 **아카이브에 넣기** |
>
> `emit_record` 의 본문은 레코드 객체를 **돌려줄 뿐**입니다 — 파일도 안 쓰고 어디로 보내지도 않습니다.
> 저장은 **브라우저 `localStorage`**(최근 20건)뿐입니다. 서버도 DB도 없습니다.
>
> ⛔**일부러 그렇게 했습니다.** 이 페이지는 **공개 배포본**입니다.
> 실제 아카이브 쓰기 권한을 여기 넣으면 **링크를 아는 누구나 남의 아카이브에 쓸 수 있게** 됩니다.
> 되돌리기 어려운 쓰기는 공개 화면 뒤에 두지 않습니다. (DECISIONS **D-20**)

> **Main Quest 4** · 내 도메인에서 사용할 에이전틱 워크플로 서비스
> **김주영** (아이펠 KDT AI 에이전트 1기) · 2026-09-09

> **한 줄** — 그림 한 점의 **제목과 작가**만 주면, 공개 데이터에서 사실을 캐고 라이선스를 판정하고
> 한국어 해설 초안까지 만들어 **사람의 승인 앞에** 갖다 놓습니다.
> **승인 없이는 아무것도 등재되지 않습니다.**

## 1. 이 워크플로가 무엇을 대신하는가

나는 신화 명화 아카이브([MYTH GALLERY](https://myth-gallery.vercel.app/ko/))를 운영합니다.
**982점**이 올라가 있고, 작품마다 기본정보·해설·신화배경·감상포인트 네 단이 붙습니다.

작품 하나를 새로 올리는 일은 매번 **같은 순서의 같은 작업**입니다.

| 단계 | 지금 걸리는 시간 | 자동화 |
|---|---|---|
| 원제·작가 확정, 표기 통일 | 5~10분 | ✅ |
| 제작연도·매체·크기·소장처를 출처 2~3곳에서 대조 | 15~25분 | ✅ |
| **퍼블릭 도메인 판정** — 아니면 올릴 수 없다 | 5~15분 | ⚠ 조회는 자동, **판정은 사람** |
| 신화 장면·등장인물 확정 | 10~20분 | ✅ |
| 한국어 해설 4단 작성 | 30~60분 | **초안까지만** |
| 기존 인물·사조와 연결, 중복 확인 | 5~10분 | ✅ |
| **합계** | **70~140분 / 점** | |

## 2. 왜 챗봇이 아니라 «에이전트»여야 했나 — 실측

한 번 물어보고 끝나는 구조로는 안 됩니다. 아카이브 20점을 층화 표본으로 뽑아 직접 재 봤습니다.

| 방식 | 적중 |
|---|---|
| 한국어 제목으로 그냥 검색 | **0 / 20 (0%)** |
| 원제(영문)로 **한 번** 검색 | **6 / 20 (30%)** |
| + 괄호·부제를 떼고 **재질의** | **12 / 20 (60%)** |
| + 작가로 스코프를 좁혀 **폴백** | 19 / 20 (95%) ※ |

> ※ 마지막 줄은 「작가 엔티티를 찾아 근거를 붙일 수 있었다」는 뜻이지 「작품을 정확히 동정했다」가 아닙니다.
> **본 평가에서는 더 엄격한 기준으로 다시 쟀습니다** — [EVALUATION.md](EVALUATION.md).

**단발 질의로는 30%.** 관찰하고 → 실패를 판정하고 → 질의를 바꿔 다시 시도하는
**루프가 있어야 나머지가 열립니다.** 이게 이 과제가 에이전트여야 하는 이유입니다.

## 3. 워크플로 둘 — 루프는 하나

**루프·상태·트레이스·승인·종료조건은 «그대로» 쓰고 규칙만 갈아 끼웁니다.**

| | **W1 등재** | **W2 큐레이션** |
|---|---|---|
| 입력 | 제목 + 작가 | 주제 한 줄 |
| 도구 | 5종 (`wd_*`·`commons_file`·`archive_search`) | 3종 (`archive_facets`·`archive_search`·`wd_entity`) |
| 결과물 | `emit_record` — 등재 JSON | `emit_exhibition` — 전시 구성 |
| **게이트가 막는 것** | 라이선스가 PD/CC 로 **확인 안 됨** · 중복 확인 **안 함** | **아카이브에 없는 작품**이 섞임 · 6점 미만 · 검색 안 함 |
| `autoRepair` | 적용 (중복 확인 대신 수행) | **적용 안 함** — 중복 확인 개념이 없음 |

**두 워크플로 모두 쓰기 도구는 «하나»뿐이고, 모델에게 보여 주지도 않습니다.**

### W1 등재

```
입력(제목·작가)
   │
   ├─ P1 계획      질의 후보를 몇 개 어떤 순서로 낼지 정한다
   ├─ P2 동정      wd_search — 실패하면 «질의를 바꿔» 다시
   │   └ P2′ 폴백  wd_sparql — 제목 검색이 «모두» 실패했을 때만
   ├─ P3 사실      wd_entity — 제작자·연도·재료·소장처·사조·묘사대상
   ├─ P4 라이선스  commons_file — ⚠불명이면 «여기서 멈춘다»
   ├─ P5 대조      archive_search — 중복 등재 여부 + 연결 후보
   ├─ P6 초안      한국어 4단. 모르는 것은 «자료 없음»으로 남긴다
   │
   ├─ ★P7 사람 승인 ─── 필드별 값 + 근거 링크 + 라이선스 배지 + 중복 경고
   │                    승인 / 수정 / 거부
   └─ P8 등재      emit_record — ★승인 상태가 아니면 «호출 자체가 거부된다»
```

**에이전트가 판단할 일**과 **도구가 처리할 일**의 구분은 [PRD.md §3](PRD.md) 표에 있습니다.

### W2 큐레이션

```
주제 한 줄
   ├─ archive_facets   어느 신화에 몇 점이 있는지 «추측하지 않고» 확인
   ├─ archive_search   주제어를 바꿔 가며 여러 번 — 후보를 모은다
   ├─ 선정·배치        8~12점을 3구획으로. 구획마다 벽면 텍스트
   ├─ ★P7 사람 승인    작품 목록을 «체크박스»로 확인 — 풀면 그 작품이 빠진다
   └─ emit_exhibition  ★아카이브에 «없는» slug 가 하나라도 있으면 거부
```

> **왜 slug 검사가 핵심인가** — 모델은 「보티첼리의 봄」처럼 **유명하지만 내 아카이브에 없는** 작품을
> 아주 자연스럽게 넣습니다. 그러면 **전시에 없는 그림이 걸립니다.** 그건 결과물이 아니라 오류입니다.
> 그래서 게이트가 `archive_search` 가 **실제로 돌려준** slug 인지 하나하나 대조합니다.

## 4. 도구 8종 — 워크플로마다 골라 쓴다

**전부 API 키가 필요 없고 CORS 가 열려 있습니다** (2026-09-09 실제 요청으로 확인, 브라우저에서도 재확인).

| 도구 | 입력 | 출력 | 실패 처리 | 권한 |
|---|---|---|---|---|
| `wd_search` | `{query, mode, artist?, lang, limit≤5}` | 후보 `[{qid,label,description}]` | 빈 결과 → **다음 질의 변형** · 429/5xx → **지수 백오프 2회** | 읽기 |
| `wd_entity` | `{qid, lang}` | 제작자·연도·재료·소장처·사조·묘사대상·Commons 파일·저작권 | 무효 qid → **P2로 되돌림** | 읽기 |
| `wd_sparql` | `{artistQid, limit≤30}` | 그 작가의 작품 목록 | 20초 타임아웃 | 읽기 · **질의 템플릿 고정**(자유 SPARQL 금지) |
| `commons_file` | `{title}` 또는 `{search}` | `{imageUrl, license, author, verdict}` | 없음 → **verdict=unknown → 등재 중단** | 읽기 |
| `archive_search` | `{q, topK≤8}` | 아카이브 982점 중 후보 | — (로컬) | 읽기 |
| `archive_facets` | `{by:"myth"\|"era"\|"people", top}` | 분포 `[{value,count}]` | — (로컬) | 읽기 |
| **`emit_record`** | 등재 레코드 | 확정 JSON | 스키마 미달 거부 | **쓰기 · ★승인 필수** |
| **`emit_exhibition`** | 전시 구성 | 확정 JSON | **아카이브에 없는 slug 거부** · 6점 미만 거부 | **쓰기 · ★승인 필수** |

### 도구 설명을 어떻게 썼나

설명은 **«무엇을 하는가»가 아니라 «언제 쓰는가»로** 씁니다. 실제 문장:

> `wd_sparql` — *"제목 검색이 «모두» 실패했을 때만 쓰는 마지막 수단. (…) 제목 검색을 시도하지 않고 먼저 부르지 말 것."*

**실측으로 발견해 설명에 넣은 것 둘:**

1. **`wd_search` 의 두 모드는 «반대로» 동작합니다.**
   `mode:"label"`(wbsearchentities)은 **라벨 접두 일치**라 작가 이름을 덧붙이면 **0건**이 됩니다.
   `mode:"fulltext"`(CirrusSearch)는 **같은 문자열로 정답을 1위**에 올립니다.
   → 설명에 이 차이를 그대로 적었고, `tools/verify-tools.mjs` 가 **이 설명이 사실인지 매번 검사**합니다.
2. **`archive_search` 에 Q번호를 넣으면 «반드시» 0건입니다.** 모델이 실제로 그렇게 했습니다.
   → *"q 에는 사람이 읽는 말을 넣는다"* 를 설명에 명시.

### 권한 최소화

- 읽기 도구 6개는 **공개 데이터와 내 아카이브만** 봅니다.
- **쓰기 도구는 워크플로마다 하나뿐**이고, 방어가 **세 겹**입니다.
  ① 모델에게 도구 목록에 **보여 주지도 않습니다**
  ② `callTool` 이 `writes:true` 도구를 승인 없이 거부
  ③ 도구 자신이 다시 한 번 검사
- `wd_sparql` 은 **자유 SPARQL 을 받지 않고** 템플릿만 채웁니다.

## 5. 에이전트 루프

`app/agent.js` · 계획 → 도구 호출 → 결과 관찰 → 다음 행동.

### 왜 네이티브 tool-calling API 를 안 썼나

**JSON 행동 프로토콜**을 씁니다 — 모델이 `{"thought":…,"action":{"tool":…,"args":…}}` 를 뱉으면 우리가 팝니다.

1. 백엔드마다 tool-calling 스키마가 달라 **«세팅을 바꿔 가며 비교»하는 이 과제의 평가가 불가능**해집니다.
2. 로컬 소형 모델은 지원이 들쭉날쭉합니다. **무료로 돌 수 있는 길을 막고 싶지 않았습니다.**
3. 트레이스에 **모델이 실제로 뱉은 문자열**이 남아 실패 원인이 보입니다.

대가는 **파싱 실패를 우리가 처리해야 한다**는 것이고, 실제로 그 처리가 필요했습니다(아래).

### 상태 관리와 재개

- `run` 객체는 **전부 직렬화 가능**합니다. 스텝마다 `localStorage` 에 저장합니다.
- 대화는 상태에서 **파생**되므로, 중단 후 되살려도 **앞 기록을 그대로 이어** 진행합니다.
- 최근 20건만 남깁니다 — 저장소가 꽉 차면 **조용히** 저장이 실패하기 때문입니다.

### 종료 조건 — 넷 (무한 루프를 막는다)

| 조건 | 기본값 |
|---|---|
| 최대 스텝 | 12 |
| 최대 도구 호출 | 20 |
| 벽시계 | 180초 |
| **같은 호출 반복** | 먼저 «관찰로» 경고 → 3회면 중단. **반복분은 실제 API 로 나가지 않습니다** |

## 6. 사람 개입과 관찰 가능성

### 승인 화면

- **필드마다 값 + 근거 링크**를 함께 보여 줍니다. **값만 보여 주면 «확인»이 아니라 «서명»이 됩니다.**
- 빈 필드는 *"자료에서 확정하지 못했습니다"* 라고 **명시**합니다 — 지어낸 값으로 채우지 않습니다.
- **승인 / 수정 / 거부** 세 갈래. 수정한 필드는 **트레이스에 남습니다**.
- **게이트가 막히면 승인 버튼이 눌리지 않습니다.**

### 안전 게이트 — 모델의 말을 믿지 않는다

`finish` 가 오면 **루프가 스스로** 두 가지를 다시 검사합니다.

1. 라이선스가 **PD/CC 로 확인**됐는가
2. **`archive_search` 로 중복 등재를 확인**했는가

**둘 중 하나라도 아니면 승인 자체가 막힙니다.** 모델이 "확인했습니다"라고 말해도 소용없습니다 —
**트레이스에 그 호출이 있는지를 봅니다.**

### `autoRepair`

중복 확인은 **읽기 전용이고 8ms** 짜리입니다. 모델이 건너뛰면 **시스템이 대신 한 번** 합니다.
⚠ **라이선스는 자동 보정하지 않습니다** — 그건 조회가 아니라 **판단**이기 때문입니다.

### 트레이스

스텝마다 **생각 · 도구명 · 인자 원문 · 결과 원문 · 도구 ms · 모델 ms · 토큰**.
파싱이 깨지면 **모델이 뱉은 문자열을 그대로** 남깁니다.
누적 토큰·비용과 **모델 시간 vs 도구별 시간** 막대로 병목을 봅니다.

### 결과물은 «실물»로 보여 준다

에이전트가 「끝냈다」고 말하는 것과 결과물이 만들어진 것은 다릅니다.
④결과 탭에 **등재 JSON 원문**과 해설 4단을 그대로 띄우고 내려받게 합니다.

## 7. 검증 — 전부 «실제로 돌려서» 확인했다

```bash
node tools/verify-tools.mjs   # 도구 30항목 — 실제 API 호출 포함
node tools/verify-loop.mjs    # 루프 30항목 — 가짜 모델로 «구조»만 시험
node tools/verify-mcp.mjs     # MCP 서버 9항목 — 실제 stdio JSON-RPC
node tools/verify-live.mjs    # 실제 모델로 한 바퀴
node tools/acceptance.mjs     # 배포된 주소로 수용 기준 재확인
```

**루프 시험에 모델을 쓰지 않는 이유** — 모델을 쓰면 실패했을 때
**«루프가 틀렸나 모델이 틀렸나»를 못 가릅니다.** 대본을 읽는 가짜 모델로 루프만 시험합니다.

검사 항목에는 이런 것들이 들어 있습니다.

- 승인 «전»에 `emit_record` 를 부르면 거부되는가
- 라이선스가 `unknown` 인데 `finish` 하면 게이트가 막는가
- 중복 확인을 건너뛰면 막는가 — **그리고 `autoRepair` 를 켜면 통과하는가**
- `autoRepair` 여도 **라이선스는 대신 판정하지 않는가**
- 같은 호출 반복 시 **실제 API 로 몇 번 나갔는가**
- 중단 → 직렬화 → 재개 후 **앞 기록이 보존되는가**
- 모델에게 쓰기 도구가 **보이지 않는가** (두 워크플로 각각)
- **큐레이션에 지어낸 slug 가 섞이면 막는가**
- `autoRepair` 가 **큐레이션에는 끼어들지 않는가**
- **도구 설명이 사실인가** (label/fulltext 모드 차이)

## 10. MCP 서버 — 내 아카이브를 «남의 에이전트»에게 연다

이 앱 안에서만 쓰이는 도구는 이 앱을 떠나면 사라집니다.

Claude Desktop 설정(`claude_desktop_config.json`):

```json
{ "mcpServers": { "myth-archive": {
    "command": "node",
    "args": ["<이 폴더>/mcp/server.mjs"] } } }
```

| 결정 | 이유 |
|---|---|
| **의존성 0** — JSON-RPC over stdio 를 직접 구현 | `npm install` 을 요구하면 「링크만으로 써 본다」는 문턱이 올라가고 `node_modules` 가 레포에 섞입니다 |

| 쓰기 도구를 부르면 **이유를 밝히며 거부** | 「없는 도구」라고 하면 왜 없는지 알 수 없습니다 |
| 에러도 «결과»로 돌려줌 | 모델이 관찰하고 다음 행동을 정할 수 있어야 합니다 |

## 11. 새로 시도한 것

- **도구 설명이 «사실인지» 검사하는 시험** — 설명에 *"label 모드는 작가명을 붙이면 0건"* 이라 적었으면
  시험이 실제로 0건인지 확인합니다. 설명과 현실이 어긋나면 **모델이 아니라 시험이 먼저 깨집니다.**
- **`autoRepair`** — 모델이 지시를 흘렸을 때 시스템이 «읽기 전용 조회만» 대신 수행. 그리고 **그것을 세팅 비교 항목으로** 측정.
- **저장된 트레이스에서 «재집계»** — 채점 규칙을 고쳐도 2시간짜리 실행을 다시 돌리지 않습니다.
  (실제로 평가 도중 실패 분류 규칙을 고쳐야 했고, `tools/report.mjs` 로 전 세팅을 같은 규칙으로 다시 매겼습니다.)
- **천장 측정(`probe-coverage.mjs`)** — 「자료의 한계」와 「에이전트의 한계」를 갈라 재기.
- **MCP 서버로 도메인 시스템을 외부 에이전트에 노출** (위 §10).
- **워크플로 둘을 «같은 루프»로** — 규칙만 갈아 끼우고 게이트는 워크플로가 정한다.
- **반복 호출을 «관찰로» 되먹임** — 조용히 죽이지 않고 모델에게 알려 스스로 빠져나올 기회를 줍니다.

## 13. 한계 — 알고 있는 것을 적는다

- **동정 정확도의 판정 기준이 «작가 일치»** 입니다. Wikidata Q번호와 아카이브 slug 사이에
  대응표가 없어 이것이 가장 강한 대리 지표였습니다. **«작품 일치»보다 약한 기준입니다.**
- **평가 40점은 전부 «이미 등재된» 작품**입니다. 진짜 신작으로는 재지 못했습니다 —
  정답지가 없으면 정확도를 잴 수 없기 때문입니다.
- **소장처 표기가 기관마다 달라** 느슨한 문자열 포함으로 채점합니다. 채점기의 관대함이 결과에 섞입니다.
- **조각·건축 사진은 «작품»이 PD 여도 «사진»에 저작권이 붙습니다.** 실행 중 실제로
  잠볼로냐 조각에 `CC BY-SA 3.0`, 베르니니 조각에 `CC BY-SA 4.0` 판정이 나왔습니다.
  지금은 그대로 사람에게 보여 주지만, **이 구분을 자동으로 설명해 주지는 못합니다.**
- **큐레이션 워크플로는 «정확도»를 잴 정답지가 없습니다.** 전시 구성에는 정답이 없기 때문입니다.
  대신 **객관적으로 잴 수 있는 것 하나**를 잽니다 — **지어낸 slug 비율**(아카이브에 없는 작품을 넣었는가).
  나머지(주제 적합성·동선의 설득력)는 **사람이 봐야 합니다.**
