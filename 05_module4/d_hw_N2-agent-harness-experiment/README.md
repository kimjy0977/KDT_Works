# 저장소 구조를 먼저 넣어 주면 「없다」는 오답이 줄어드는가

> 모듈4 노드2 [프로젝트] 과제 · 김주영 (아이펠 KDT AI 에이전트 1기)
> 논문의 수치는 정답이 아니라 **조건이 붙은 가설**이다. 내 환경에서 재현하거나 반박할 근거로만 쓴다.

**상태:** 실행 완료 (1회차 6시행) · **가설 기각**
**기준 도구:** Claude Code
**조작 항목:** 하네스 기능 중 **메모리 표현** 하나

## 1. 불편 — 어떤 과업에서, 어떤 입력 뒤에, 무엇이 잘못되었나

**장면 (2026-09-08, 강의노트 감사 작업 중).**

같은 세션이 길어져 대화가 한 번 **압축(컴팩션)**된 직후, 나는 에이전트에게
"미결 항목 중 `HANDOFF-튜터.md` 갱신이 남았는지 확인해 달라"고 요청했다.

에이전트는 `find`를 **`-maxdepth 4`** 로 **한 번** 돌려 보고
**"핸드오프 파일은 존재한 적이 없습니다"** 라고 단정했다.

실제로는 `00_shared/repos/KDT_Works/00_log/HANDOFF-튜터.md`에 **있었다. 깊이 5였다.**
잘못된 단정은 그대로 사용자에게 보고됐고, **30분쯤 뒤 다른 작업 중에 우연히** 드러났다.

### 왜 이것이 「하네스 기능」의 문제일 수 있는가

압축 전 대화에는 이 파일의 경로가 여러 번 등장했다. **압축은 그 경로를 버렸다.**
남은 것은 "핸드오프 갱신이 미결"이라는 요약 문장뿐이었고,
에이전트는 사라진 경로를 **탐색으로 복구하려다 스스로 정한 얕은 깊이에서 멈췄다.**

곧 **문맥 관리라는 하네스 기능이 「무엇을 버리는가」** 의 문제로 보인다.

### 의심해야 할 다른 원인 — 이 실험이 반드시 구분해야 할 것

| 후보 원인 | 왜 의심스러운가 | 어떻게 가르나 |
|---|---|---|
| ① **하네스의 문맥 압축** | 경로가 압축 과정에서 사라짐 | 압축 여부를 고정하고 **메모리 표현**만 바꾼다 |
| ② **내 요청 문장** | "확인해 달라"가 탐색 범위를 지정하지 않음 | 세 과업의 요청 문장을 **글자까지 고정** |
| ③ **탐색 도구 사용 습관** | `maxdepth`를 임의로 정한 것은 모델의 선택 | 도구 목록·권한을 양쪽 조건에서 동일하게 |
| ④ **저장소 상태** | 파일이 실제로 그 시점에 없었을 가능성 | fixture 저장소를 **고정**하고 변경 금지 |
| ⑤ **모델 차이** | 모델이 바뀌면 결과가 바뀐다 | 같은 모델·같은 설정 |

> ②③이 진짜 원인이라면 이 실험은 **기각되어야 한다.** 그렇게 설계했다.

## 2. 근거 — 등급을 구분해 인용한다

내 가설은 **새로 지어낸 것이 아니라 이미 제품이 채택한 설계**다.
그래서 「그 주장이 내 환경에서도 성립하는가」를 확인하는 형태로 만들었다.

| # | 출처 | 등급 | 원문이 말하는 것 | **검증하지 않은 것 / 한계** |
|---|---|---|---|---|
| 1 | **Aider `repo map`** (벤더 설계글, 2023-10-22) | `[벤더]` | 큰 저장소의 파일을 전부 넣으면 문맥 창이 넘친다. 대신 **저장소의 뼈대만 담은 기호 지도**를 만들어, 정의·참조의 graph ranking으로 **기본 1천 토큰 예산** 안에서 항목을 골라 넣는다. 모델은 그 지도를 보고 **필요한 파일만** 첨부한다 | **독립 성능 비교가 아니다.** 제작사의 설계 설명이며 대조군과 비교한 수치가 없다 → **이 실험이 재현·반증하려는 대상** |
| 2 | **SWE-agent** (Yang et al., NeurIPS 2024, arXiv:2405.15793) | `[학술]` | SWE-bench Lite에서 **최근 5개 관측은 자세히, 과거는 축약**한 조건이 **18.0%**, 전체 이력 조건이 **15.0%** → **+3.0%p**. 같은 과업·모델에서도 **관측을 고르는 방식이 결과를 바꾼다** | 해당 **모델·과업 조건에 붙은 수치**다. "5개가 늘 최적"이라는 뜻이 아니며 다른 모델·과업으로 일반화하지 않는다 |
| 3 | **RAG vs long-context** (Li et al., EMNLP 2024 Industry, arXiv:2407.16833) | `[학술]` | **예산이 충분할 때 long-context가 평균 성능에서 일관되게 RAG보다 높았고**, RAG의 장점은 **비용**이라고 보고 | **내 가설과 반대 방향의 근거.** 정보를 골라 넣는 것이 항상 이득은 아니다 → **기각 가능성의 근거로 명시한다** |
| 4 | **Anthropic 문맥 설계 원칙** (공식 문서) | `[공식 문서]` | 문맥은 단순한 저장 공간이 아니라 **매 요청에서 제한된 입력 예산을 배분하는 대상** | **설계 원칙**이며 **특정 요약·주입 정책의 성능을 보증하지 않는다** |

### 이 표에서 내가 읽은 것

`[벤더]`인 **①은 "된다"고 말하지만 비교 수치를 대지 않는다.**
`[학술]`인 **②는 "관측 선택이 결과를 바꾼다"를 실제 수치로 보이지만 조건이 좁다.**
그리고 `[학술]`인 **③은 반대 방향을 가리킨다.**

셋을 겹치면 남는 질문은 하나다 — **내 과업에서는 어느 쪽인가.**

## 3. 가설 — 반증 가능하게

> **H.** 세션 시작 시 **저장소의 파일 경로 목록을 고정 형식으로 문맥에 넣어 두면**,
> 넣지 않았을 때보다
> **① 존재하는 파일을 「없다」고 단정하는 오류가 줄고**
> **② 그 파일에 닿기까지의 탐색 도구 호출이 줄어든다.**

**이것은 Aider `repo map`의 축소판이다.** 기호 지도 대신 **경로 목록**을 쓰고, 자동 선별 대신 **전량 주입**한다.

### 반증 조건 — 이 결과가 나오면 가설을 버린다

- 처치 조건에서 **존재 부정 오류가 같거나 더 많다**, 또는
- **탐색 호출 수가 줄지 않는다** (±1 이내면 「변화 없음」으로 본다), 또는
- **T3에서 「없다」를 못 하게 되는 부작용**이 나타난다

### 고정

| 항목 | 값 |
|---|---|
| 도구 | Claude Code (동일 버전) |
| 모델 | 같은 모델·같은 설정 |

### 조작 — 「메모리 표현」 한 가지만

| 조건 | 내용 |
|---|---|
| **A (대조)** | 아무것도 넣지 않고 과업 문장만 보낸다 |
| **B (처치)** | 과업 문장 **앞**에 `fixtures/tree.txt`(경로 목록 7줄)를 **그대로** 붙인다 |

### 측정 — 해결률만 적지 않는다

| 지표 | 세는 법 |
|---|---|
| **존재 부정 오류** | "없습니다 / 존재하지 않습니다 / 찾을 수 없습니다"로 **단정**했는데 실제로는 있는 경우의 **건수** |
| **탐색 도구 호출 수** | `Glob`·`Grep`·`Bash(find/ls)` 계열 호출 **횟수** |
| **정답 여부** | 최종 답이 정답과 일치하는가 (O/X) |
| **소요 시간** | 요청 → 최종 답변 |
| **턴 수** | 도구 호출을 포함한 왕복 수 |

### 과업 3개 — `fixtures/repo/` 안에서

| # | 과업 | 정답 | 노리는 것 |
|---|---|---|---|
| **T1** | "이 저장소에 핸드오프 문서가 있는지 확인하고, 있으면 경로를 알려 줘." | `docs/internal/ops/handoff/HANDOFF-tutor.md` | **깊이 5**에 숨긴 파일 — 얕은 탐색이면 놓친다. **원 사고의 재현** |
| **T2** | "이 저장소에 설정 파일이 몇 개인지 세어 줘." | `settings.toml` **3개** | 여러 폴더에 흩어짐 — **집계**가 필요하다 |
| **T3** | "README.md 가 참조하는 문서 중 실제로 없는 것을 찾아 줘." | `docs/CONTRIBUTING.md`, `SECURITY.md` | **여기서는 「없다」가 정답이다** — 통제 문항 |

> **T3이 통제 문항인 이유.** 처치 B가 「없다는 말을 못 하게 만드는」 부작용을 내는지 본다.
> 경로 목록을 넣었더니 목록에 없는 파일까지 「있다」고 하거나, 목록만 보고 **README를 안 읽고** 답한다면 그것도 실패다.

### 예상 반론과 통제

| 반론 | 통제 |
|---|---|
| "파일 목록을 줬으니 당연히 맞힌다 — **정보를 그냥 준 것** 아닌가" | 그래서 **탐색 호출 수와 시간도 함께** 잰다. **맞히기만 하고 비용이 그대로면** 「표현」의 이득이 아니다. 또한 T2·T3은 목록만으로는 답이 나오지 않는다(**세어야** 하고, **README를 읽어야** 한다) |
| "요청 문장이 유도했다" | 세 문장을 **글자까지 고정**해 저장소에 넣어 뒀다 |
| "한 번은 우연" | 각 조건 **3회 반복**, **중앙값**으로 비교 |
| "근거 ③처럼 오히려 손해일 수 있다" | **그렇다.** 그 가능성을 §2에 명시했고, 기각 조건을 §3에 적었다 |

## 5. 사전 판정식 — 결과를 보기 「전에」 적는다

> **지지:** 3과업 중 **2개 이상**에서
> ① 존재 부정 오류가 **B < A** **그리고** ② 탐색 호출 수가 **B ≤ A − 2**
>
> **기각:** 그 외 전부.
> 특히 **T3에서 B가 「없다」를 못 하게 되면 부작용으로 기록하고 기각**한다.
>
> **판정 불가:** 3회 반복의 중앙값이 조건 간 ±1 이내로만 갈리면 **「차이 없음」**으로 적고 지지로 세지 않는다.

### 사전 판정식(§5) 대조

| 과업 | 조건① 오류 B<A | 조건② 탐색 B ≤ A−2 | 판정 |
|---|---|---|---|
| T1 | 0 → 0 · **NO** | 1 → 1 · **NO** | 미충족 |
| T2 | 0 → 0 · **NO** | 2 → 1 · **NO** | 미충족 |
| T3 | 0 → 0 · **NO** | 2 → 2 · **NO** | 미충족 |

**충족 과업 0개 / 지지 기준 2개 → 가설 기각.**

### ★관찰된 것 — 「대조군에서도 오류가 0이었다」

가설이 틀린 것보다 **먼저 봐야 할 사실**이 있다.

> **조건 A(목록 없음)에서도 존재 부정 오류가 0이었다.**
> 즉 **이 실험은 원래 불편(§1)을 재현하지 못했다.**

이유는 실행 기록에 그대로 적혀 있다. **조건 A의 에이전트들이 `find . -type f` 를 깊이 제한 없이 돌려 7개 파일을 전수 열거했다.**
T1-B의 답변에는 이렇게 적혀 있다 — *"저장소 전체 파일이 7개뿐이라 `find` 한 번으로 전수 확인했고"*.

**원 사고는 「깊이를 잘라서」 생긴 것인데, 이 fixture에서는 깊이를 자를 이유가 없었다.**
7파일짜리 저장소에서는 전수 열거가 가장 싼 선택이기 때문이다.

### 부수 관찰 셋

| 관찰 | 내용 |
|---|---|
| **T3 부작용 없음** | 목록을 넣은 B에서도 「없다」 판정이 유지됐다(`docs/CONTRIBUTING.md`·`SECURITY.md` 정확히 지목). **목록에 없는 파일을 「있다」고 하지 않았다.** 통제 문항 통과 |
| **탐색 1회 감소(T2)** | T2에서만 2→1로 줄었다. 다만 **1회 차이는 §5가 「변화 없음」으로 규정한 범위**이며, n=1이라 우연과 구별되지 않는다 |

## 7. 불편의 진짜 원인이 「하네스 기능」이었나 — 되돌아보기

**아니었을 가능성이 커졌다.** 정확히는 — **이 실험으로는 「하네스 기능이 원인」이라는 설명을 지지할 수 없다.**

### §1에서 세운 후보 원인 다시 보기

| 후보 | 실험 후 판단 |
|---|---|
| ① 하네스의 문맥 압축 | **검증되지 않음.** 이 설계는 압축을 유발하지 않고 「새 세션 + 목록 유무」로 상황을 흉내 냈을 뿐이다. **압축을 조작하지 않았으므로 ①에 대해 말할 수 있는 것이 없다** |
| ② 내 요청 문장 | **배제됨.** 문장을 글자까지 고정했고, 같은 문장에서 조건 A도 정답을 냈다 |
| ③ **탐색 도구 사용 습관** | **★가장 유력해졌다.** 조건 A의 에이전트들은 `maxdepth` 없이 전수 열거했고 즉시 정답을 냈다. **원 사고의 나는 `maxdepth 4`를 스스로 붙였다.** 같은 도구·같은 저장소인데 **탐색 범위를 임의로 좁힌 선택**이 갈랐다 |
| ④ 저장소 상태 | 배제됨. fixture를 고정했고 매 실행 전 확인했다 |
| ⑤ 모델 차이 | 배제됨. 6시행 모두 같은 모델 |

### 무엇이 원인 설명을 약하게 만들었나

**fixture가 너무 작았다.** 7파일 저장소에서는 **「무엇을 볼지 고르는 문제」 자체가 발생하지 않는다.**
전수 열거가 싸니까 아무도 범위를 좁히지 않고, 그러면 **경로 목록을 미리 주는 이득도 생길 자리가 없다.**

근거 ③(RAG vs long-context)이 말한 것이 바로 이것이다 — **예산이 충분하면 골라 넣을 이유가 없다.**
7파일은 「예산이 충분한」 극단이었다. **내 가설은 예산이 모자란 조건에서만 시험할 수 있는 가설이었는데, 그 조건을 만들지 않았다.**

### 다음 실험에서 고정하거나 바꿀 조건

1. **저장소 규모를 키운다** — 전수 열거가 부담스러운 크기(수백~수천 파일)로. 그래야 탐색 범위를 좁히는 행동이 나타난다
2. **압축을 실제로 유발한다** — 세션 길이를 고정해 압축이 일어난 뒤에 질문한다. 그래야 후보 ①을 검증할 수 있다
3. **후보 ③을 직접 조작해 본다** — 「탐색 범위를 좁히지 말라」는 지시 한 줄의 유무를 비교하면, 지금 가장 유력한 원인을 바로 시험할 수 있다

## 8. 다시 검토할 조건 (실행 후 갱신)

### 이번 실행의 한계 — 결과를 읽을 때 반드시 함께 볼 것

| 한계 | 내용 |
|---|---|
| **「새 세션」의 대용** | 실제 Claude Code 세션 6개가 아니라 **부모 세션이 띄운 서브에이전트의 격리 컨텍스트**로 돌렸다. 도구 구성은 같지만 **동일하다고 주장하지 않는다** |
| **탐색 호출은 자기보고** | 서브에이전트의 도구 호출 내역이 부모 세션에 노출되지 않아 **에이전트가 스스로 센 값**을 받았다. 게다가 **「세어서 보고하라」는 지시 자체가 탐색을 아끼게 만들었을 수 있다**(양 조건에 동일하게 들어갔으나 절대값은 신뢰하지 않는다) |
| **n = 1** | §4가 정한 **3회 반복을 채우지 못했다.** T2의 탐색 1회 감소는 우연과 구별되지 않는다 |
| **★압축을 조작하지 않았다** | 원 사고의 핵심 조건을 재현하지 못했다. **이것이 이번 기각의 가장 큰 원인이다** |
| **fixture가 7파일** | 「무엇을 볼지 고르는 문제」가 발생하지 않는 크기였다 |
| **경로 목록 ≠ `repo map`** | Aider는 정의·참조를 랭킹해 예산 안에서 **고르는데**, 이 실험은 **전량 주입**이다. **선별의 효과는 측정하지 않았다** |

### 이 결과로 말할 수 있는 것과 없는 것

- **말할 수 있는 것** — *7파일 규모의 저장소에서, 압축 없는 새 컨텍스트라면, 경로 목록 주입은 정답률·탐색 횟수에 의미 있는 차이를 만들지 않았다. 그리고 「없다」를 못 하게 만드는 부작용도 없었다.*
- **말할 수 없는 것** — Aider `repo map`의 주장이 틀렸다는 것. **이 실험은 그 주장이 성립할 조건(큰 저장소·제한된 예산)을 만들지 않았으므로 반박이 되지 못한다.**
