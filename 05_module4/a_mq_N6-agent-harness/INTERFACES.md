# 인터페이스 계약
상태: 초안. 아래는 언어와 통신 방식에 독립적인 설계 틀이다. 학생의 D02~D07 선택 후 구체적 타입, 예시와 오류를 채운다. API는 프로그램 사이의 약속이며 HTTP만 뜻하지 않는다.

## 제품의 작업 계약
| 동작 | 입력에서 정할 것 | 출력에서 정할 것 | 오류·경계 |
|---|---|---|---|
| 작업 시작 | 요청, 세션 선택, 작업 폴더 식별 | 작업 식별자와 최초 상태 | 빈 요청, 없는 세션, 실행 중 중복 요청 |
| 상태 조회 | 작업 식별자 | 상태, 진행 내역, 결과 또는 오류 | 없는 작업, 다른 세션의 작업 |
| 변경 승인/거절 | 작업·승인 식별자, 표시한 변경에 대한 선택 | 결정 반영 결과 | 중복/만료 승인, 승인 후 변경 내용 바뀜 |
| 결과 조회 | 작업 식별자 | 결과, 근거, 변경·테스트 기록 | 미완료를 완료로 보여 주지 않음 |
| 세션 이어가기 | 세션 식별자, 새 요청 | 연결된 새 작업 | 재시작 후 기록이 없으면 복원했다고 말하지 않음 |

작업 상태 제안: queued → running → waiting_approval → running → completed/failed. 선택한 기능에 따라 cancelled 추가. **실제 사용 상태(2026-09-08 실측)** — `completed` · `step_limit` · `failed` 셋만 쓴다. CLI가 대화형이라 `queued` 는 필요 없고, 승인은 **같은 프로세스가 그 자리에서** 받으므로 `waiting_approval` 을 별도 상태로 두지 않았다. `cancelled` 는 D09에서 제외. **거절 이후** — 실패로 끝내지 않고 **오류 결과를 모델에게 돌려주어 재계획**하게 한다(A04 실측). ★`completed` 는 «모델이 텍스트를 반환했다»는 뜻이지 «업무 정답»이 아니다.
승인은 특정 작업의 특정 도구 입력/변경 내용에 연결한다. 사용자가 본 내용이 바뀌면 그 승인을 재사용하지 않는다.

### 구체적 계약 한 개
- 이름: `read_file`
- 입력 타입과 허용 범위: `path` **문자열 1개**. 작업 폴더 상대경로, 또는 **작업 폴더 «안»의 절대경로**. 상위 이동(`..`) · 숨김(`.`) · 심볼릭 링크 · 500자 초과는 거부
- 정상 입력 예: `{"path": "meeting.txt"}`
- 정상 출력 예: `{"event":"tool_end","name":"read_file","call_id":"call_mfpmlvii","ok":true}` + 파일 내용이 대화에 추가된다 **(2026-09-08 실측)**
- 잘못된 입력과 오류 출력 예: `{"path": "../pyproject.toml"}` → `ok:false` · `Local tool execution rejected (ValueError): Path leaves workspace` **(A05 실측)**. ★**파일 없음**과 **빈 파일**은 다른 결과다 — 없으면 오류, 비어 있으면 `ok:true` + 빈 내용
- 상태 변화/부작용: **없음(읽기 전용).** 파일을 바꾸지 않는다
- 재시도·중복 요청 정책: **멱등.** 반복 호출하면 그때의 최신 내용을 읽는다. 승인도 필요 없다
나머지 동작에도 같은 틀을 적용한다. API의 모든 필드를 모델의 자연어 판단에 맡기지 않는다.

## UI와 통신 매핑
CLI를 선택하면 명령/옵션과 내부 함수 호출을 위 계약에 대응한다. 로컬 웹을 선택하면 HTTP 메서드·경로·본문·응답 코드와 인증 범위를 정한다. CLI 구현에 웹 서버를 의무적으로 추가하지 않는다.
- 선택한 방식: **로컬 CLI** (D02)
- 명령 또는 HTTP 경로와 계약의 대응: `run.py --provider --model --workspace --session --prompt` → 「작업 시작」. 별도의 조회·승인 명령 없이 **같은 프로세스 안에서** 승인을 받는다(대화형 CLI라 작업 ID 조회가 필요 없다 — 이 단순화의 대가는 «실행 중 다른 터미널에서 상태를 볼 수 없다»는 것)
- 진행 결과를 보여 줄 방식: **JSON 이벤트를 한 줄씩** 출력 — `model_start` → `tool_start` → `tool_end`(ok) → `run_end`(status·metrics). 사람이 읽는 최종 답은 그 뒤에 따로 출력

## 모델 제공자 연결부
제품 내부에서는 모델에게 전달할 대화/도구 정보와 돌려받을 최종 답/도구 요청을 정한다. provider adapter는 각 제공자의 요청·응답을 이 내부 계약으로 변환한다.
- 첫 제공자/모델: **Ollama · qwen3.5:2b** (D04). `capabilities` 에 `tools` 포함을 확인하고 골랐다
- 사용 API와 공식 문서: Ollama **네이티브 `/api/chat`**. ⚠ OpenAI 호환 경로를 **가정하지 않는다** — 제공 구현도 네이티브를 쓴다
- 도구 호출·결과 연결에 필요한 식별자 처리: 호출 ID(`call_mfpmlvii` 형태)로 요청과 결과를 잇는다. **Ollama 응답에는 호출 ID가 없어 어댑터가 내부 ID를 붙인다** — 이를 «서버가 발급한 ID»라고 적지 않는다
- 일반 답과 도구 호출, 여러 도구 요청의 처리 순서: 도구 요청이 **없는** 텍스트를 받으면 종료. 요청이 있으면 **인수 검사 → 권한 검사 → 실행 → 결과를 대화에 추가 → 다시 모델 호출**. 여러 요청은 받은 순서대로 처리
- 지원하지 않는 기능, 파싱 실패, 네트워크 오류: **오류로 알린다.** 빈 답변으로 바꿔 숨기지 않는다. 도구 인수 오류는 모델에게 돌려주어 수정 기회를 주고, 연결 «자체» 실패는 사용자에게 표시한다. **⚠ 미검증** — 연결 자체 실패는 아직 시험하지 않았다(A07 한계)
- 제한 횟수/시간과 재시도 대상: D09의 한도. **자동 재시도는 넣지 않았다** — 실행 여부가 불확실한 작업을 자동 반복하면 부작용이 두 번 생길 수 있다(6강 멱등성)
OpenAI와 Ollama에 같은 필드를 보내면 언제나 같은 기능이 동작한다고 가정하지 않는다. 모델 응답은 실행 전에 구조와 인자를 검사한다.

## 실행 도구 계약
| 도구 | 인자/반환 예 | 허용 범위 | 승인·오류 |
|---|---|---|---|
| `read_file` | `{"path":"meeting.txt"}` → 파일 내용 | `work/` 안 | 승인 불필요 · 경로 이탈 `Path leaves workspace` · 없는 파일은 오류(빈 내용과 **구별**) |
| `write_file` | `{"path":"receipt.py","content":"…"}` → 적용 여부 | `work/` 안 | **전체 내용을 보여 주고 y/n** · 거절 시 파일 불변(A04 실측) · 충돌 처리는 **미구현**(한계로 기록) |
| `run_command` | `{"argv":["python","-m","unittest","discover","-s","work"]}` → 종료 코드·출력 | `work/` 에서 실행 · **셸 해석 없음** | 승인 필요 · 도구당 30초 · ⚠ **테스트 프로세스는 내 계정 권한** — 작업 폴더 격리가 아니다 |
실행 도구 내부의 파일·명령 검사는 모델의 지시와 무관하게 적용한다. 임의 셸 명령을 허용하는 것은 별도의 권한 확대다.
