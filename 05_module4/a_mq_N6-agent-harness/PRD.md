# 개인 에이전트 하네스 PRD
상태: 설계 대화 전. OPEN을 AI가 임의로 채우지 않는다.

## 제공된 제품 목표
사용자가 자연어로 작업을 요청하면 모델이 필요한 도구를 선택하고, 내 프로그램이 이를 검사·실행하여 결과를 다시 모델에 전달한다. 자료를 읽는 범용 작업과 코드를 수정하고 검증하는 코딩 작업을 모두 다룬다. 사용자는 진행 상황과 실패 이유를 확인할 수 있다.
PRD(Product Requirements Document)는 무엇을 누구를 위해 만들고 어떤 결과를 완료로 볼지 기록한다. 구현 방법의 모든 세부사항을 미리 고정하는 문서는 아니다.

## 학생이 완성할 사용자 이야기
D01 사용자/업무: CHOSEN
- 나는 **KDT 과정을 듣는 학습자 본인**으로서 **회의록·체크리스트 같은 짧은 기록 파일**과 **작은 파이썬 검사 스크립트**에 **정리와 수정** 작업을 하고 싶다.
- 지금 불편한 점:
  - (자료) 회의록이 날짜별로 나뉘어 있어, 무엇이 **확정됐고** 무엇이 **아직 담당자도 안 정해졌는지**를 매번 여러 파일을 열어 맞춰 봐야 한다.
  - (코드) 검사 스크립트가 **틀린 곳을 못 찾는 게 아니라, 멀쩡한 곳을 틀렸다고 말한다.** 어디가 진짜 오류인지 사람이 다시 걸러야 한다.
- 실제로 성공했다고 판단할 결과:
  - (자료) 확정된 일과 확인이 필요한 일이 **구별되어** 나오고, **어느 파일의 어느 문장**에서 나왔는지 함께 보인다. **담당자가 안 정해진 항목을 임의로 채우지 않는다.**
  - (코드) 실패하던 검사가 통과하고, **원래 통과하던 검사도 그대로 통과한다.** 변경 내용과 다시 실행한 결과를 함께 보여 준다.
- 원하지 않는 행동:
  - (자료) 없는 담당자나 일정을 **추측해 확정**하는 것.
  - (코드) 검사의 **기대값을 바꿔** 실패를 숨기는 것.
- 실습용 자료: `fixtures/notes/` (회의록 2건 + 체크리스트, 민감정보 없음) · `fixtures/code/` (`tagcheck.py`, `test_tagcheck.py` 5건 중 2건 실패, `sample.html`)

## 학생의 선택
D02 플랫폼: CHOSEN — **내 컴퓨터에서 실행하는 CLI.** 요청·진행·결과와 파일 변경 승인을 모두 터미널에서 확인한다. 화면도 도구 실행도 같은 내 노트북이며, 원격 접속은 이번 범위에서 제외한다.
D03 언어: CHOSEN — **Python.** 최근에 배운 함수·파일 처리 문법으로 실행 흐름을 직접 읽고 검증할 수 있다. fixture의 검사 스크립트도 Python이라 같은 언어 안에서 끝난다.
D04 첫 provider: OPEN — 제공된 OpenAI API 키 / Ollama의 로컬 모델 등. 실제 모델과 도구 호출 지원 여부는 구현 시 확인한다.
D05 첫 작업과 도구 범위: OPEN — 먼저 읽기 한 작업, 이후 쓰기와 테스트. 접근할 실습 폴더와 허용할 실행을 정한다.
D06 승인 방식: OPEN — 무엇을 보여 주고 어떤 행동에 대해 받는 승인인지 정한다.
D07 세션과 저장: OPEN — 첫 버전에서 메모리만 유지할지 파일로 저장할지, 재개 의미와 한계를 정한다.
D08 추가 provider: OPEN — 전환/비교 기능을 넣을지 나중으로 미룰지 정한다.
D09 확장 기능: OPEN — 취소, 진행 이벤트, 동시 실행, 원격 접속 등에서 필요한 것을 선택하거나 미룬다.

## 최초 범위와 제외 범위
최초 범위: **로컬 CLI 하나**에서 ①자료 읽기(`read_file`) ②승인 후 파일 변경(`write_file`) ③승인 후 고정 테스트 실행(`run_command`) ④세션 파일 저장 ⑤한도와 실행 기록. 작업 폴더는 `work/` 한 곳, 제공자는 Ollama 하나.
후속 범위: 코드 수정/테스트와 해당 권한 검사, 나머지 합의 기능.
이번 버전에서 제외: **OpenAI 제공자**(선불 크레딧 없음 · D08) · **취소/동시 실행/원격 접속**(D09 — 한도와 기록만으로 「멈추는 이유」를 남기는 것이 우선) · **승인 대기 중 파일이 사람 손에 바뀌는 충돌 처리**(6강이 요구했으나 미구현 — 「갖췄다」고 쓰지 않고 한계로 남긴다) · **임의 셸 명령**(D05 — argv 배열만 받는다).
기본 제외: 공개 원격 제어 서비스, 임의 시스템 전체 접근, 비밀키 공유. 원격 접속은 별도 설계 없이는 추가하지 않는다.

## 완료 기준
ACCEPTANCE.md의 공통 시나리오에 실제 증거를 남긴다. 실제 모델 한 종류에서 범용 작업과 코딩 작업을 확인하고, 오류·거절도 검증한다. 추가 provider와 저장 재개는 선택한 범위에 따라 확인하거나 제외 사유를 쓴다. 모델 응답의 품질과 프로그램의 도구 실행 성공은 별개로 평가한다.

## 벤치마크 실험
Docker 없이 실행하는 Terminal-Bench Pro 로컬 이식판의 고정 목록으로, 원본 easy 2·medium 4·hard 4를 사용한다. 실행 가능한 Python 예시와 로컬 평가 연결·점수 모니터는 별도 harness-lab 자료로 제공한다. 자신의 구현을 같은 로컬 평가 규격에 연결하거나 예시를 이해하고 개선한다. 높은 점수 자체가 완료 조건은 아니며, 기준 측정과 가설에 따른 변경 후 측정의 실제 결과를 제출한다. 오류·미완료를 분모에서 제외하지 않고 개발용 채점기 진단과 학생 모델 성능을 구별한다.

난이도는 고정된 upstream task.toml의 분류를 유지한다. 경로와 Python 실행을 로컬로 이식한 결과이며 공식 컨테이너 점수가 아니다. 더 다양한 환경을 일관되게 재현할 때 Docker를 사용할 수 있으나 기본 과제에서는 요구하지 않는다.
