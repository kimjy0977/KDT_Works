## 1. ★채점기부터 읽었습니다 — 코드를 봐야만 보이는 것 셋

고치기 전에 `evaluate.py` 를 정독했습니다. **무엇으로 재는지 모르면 어디를 고칠지도 모릅니다.**

| 발견 | 코드 | 그래서 |
|---|---|---|
| `norm_num` 은 **콤마만** 지운다 | `re.sub(r"(?<=\d),(?=\d)", "", s)` | 「50,000원」은 통과 · **「5만원」은 실패** |
| 도구는 **«더» 불러도 감점이 없다** | `need - set(tools_called)` — 미호출만 본다 | **애매하면 더 부르는 쪽이 이득** |
| ★**ASK 판정이 «도구를 안 불렀을 때»만 된다** | `elif not results and re.search(...)` | ASK 기대인데 도구를 하나라도 부르면 **실패** |

### ★★세 번째가 문제입니다 — **프롬프트와 채점기가 서로 반대를 요구합니다**

```
prompts.py  「도구를 부를 수 있는데도 부르지 않고 되묻는 것은 실패다」
evaluate.py 「도구를 불렀으면 ASK 가 아니다」
```

**채점 32건 중 ASK 가 8건(25%)입니다.** 프롬프트를 그대로 따르면 8건이 통째로 날아갑니다.

⇒ 이건 **12강이 한계로 명시한 자리**이기도 합니다 —
*「검색을 적극적으로 시키자 조회 성공률은 올랐지만, 되물어야 할 문의에 답해 버리는 건수도 함께 늘었다.
두 축이 «반대로» 움직이는 교환 관계이고, 어느 쪽을 감수할지는 «도메인»이 정한다」*

## 2. ★다른 팀이 헛수고하고 있을 결함 하나

```python
router.py:16   from config import CONF_THRESHOLD, MODEL   # 가져오고
router.py:50   CONF_THRESHOLD = 0.5                       # ★바로 아래서 «덮어쓴다»
```

`gate()` 가 읽는 것은 **아래쪽 값**입니다. 그런데 `config.py` 주석은
**「여기 값만 바꿔도 동작이 달라진다」**고 적혀 있습니다. **이 값만은 안 달라집니다.**

⇒ **「임계값을 조정해봤는데 숫자가 안 움직이더라」**는 팀이 있다면,
그건 **효과가 없었던 게 아니라 «바뀐 적이 없는»** 겁니다.

⇒ 왜 이렇게 됐나 — 강의는 **노트북 한 파일**이라 `global CONF_THRESHOLD` 로 바꾸면 먹힙니다.
그걸 **패키지로 쪼개면서** 모듈 경계가 생겼고, **덮어쓰는 줄이 그대로 따라왔습니다.**

⇒ 그리고 이건 **6강이 남긴 숙제를 «실행할 수 없게»** 만듭니다 —
*「확신도는 모델이 스스로 보고하는 값이라 «틀린 확신»도 있을 수 있다.
확신도 «자체»를 평가셋으로 검증해야 한다」* — 그 검증에 쓸 손잡이가 끊겨 있습니다.

## 4. ★LLM 으로 갈아 끼웠더니 — **나빠졌습니다**

| # | 무엇 | 정확도 | macro F1 | outscope | 형식실패 |
|---|---|---|---|---|---|
| — | **규칙 라우터**(4강) | 0.583 | **0.677** | 84.8% | — |
| 0 | **Ollama 2B · 지침만**(6강) | 0.542 | **0.556** | 78.8% | 0 |
| 1 | Ollama 2B · **+fewshot** | **0.633** | **0.667** | **84.8%** | 0 |
| 2 | Ollama 2B · **v2** (SHIPPING 강화 **+ OTHER 억제**) | **0.742** | **0.755** | ⛔ **57.6%** | 0 |
| 3 | Ollama 2B · **v3** (SHIPPING 강화 **만**) | 0.717 | 0.738 | ⛔ **57.6%** | 0 |
| 4 | Ollama 2B · **v4** (「보내지 말고」→「든다」) | 0.725 | 0.741 | 60.6% | 0 |
| 5 | ★**v4 + fewshot** | 0.792 | 0.816 | 66.7% | 0 |
| **6** | ★★**7b · v4 + hard-fewshot** | **0.925** | **0.925** | **75.8%** | 0 |

6강은 규칙 → LLM 교체를 **개선으로 전제**합니다. **작은 모델에서는 역전됩니다.**

### ★★그리고 fewshot 을 붙이자 — **어느 지표를 보느냐로 결론이 «뒤집힙니다»**

```
정확도로 보면    0.633 > 0.583   ⇒ 「LLM 이 규칙을 이겼다」
macro F1 로 보면 0.667 < 0.677   ⇒ 「아직 못 이겼다」
```

원인은 **SHIPPING 하나**입니다. 세 라우트는 크게 올랐는데(ORDER_PLACE 0.542→0.708 ·
PRODUCT_INFO 0.836→0.900 · RETURN_REFUND 0.784→0.830) **SHIPPING 만 0.062→0.229** 로
못 따라옵니다. macro 평균은 클래스마다 **동등한 무게**를 주므로 이 하나가 전체를 끌어내립니다.

⇒ 5강이 *「소수 라우트의 실패도 그대로 보고 싶으므로 macro F1 을 주 지표로 삼는다」*
고 한 이유가 **숫자로** 나왔습니다. **지표를 하나만 보면 반대 결론에 도달합니다.**

### ★outscope 를 «같이» 잰 것이 값을 했습니다

```
지침만    eval 0.542 · outscope 78.8%
+fewshot  eval 0.633 · outscope 84.8%   ← 둘 다 올랐다
```

**eval 만 올리고 범위 밖을 희생한 «지표 해킹»이 아닙니다.**
평가셋 120건에는 OTHER 정답이 **0건**이라, OTHER 를 덜 쓰게만 만들어도 eval 점수는 오릅니다.
그 대가는 `evaluate.py` 가 **안 잽니다.** 그래서 매번 둘을 같이 쟀습니다.

### ★그리고 실패 방식이 «같습니다»

```
규칙 라우터    오분류 50건 중 40건이 → OTHER  (80%)
Ollama 2B      오분류 55건 중 31건이 → OTHER  (56%)
```

**둘 다 모르면 OTHER 로 도망갑니다.** 방식이 다른 게 아니라 정도가 다를 뿐입니다.

## 6. ★★가장 값진 실패 — 첫 실행이 **20/20 «형식» 실패**였습니다

```
구조화 출력 실패 20건 · OutputParserException
```

원인은 **`qwen3` 계열의 thinking 모드**였습니다. 출력 예산이 thinking 에 다 쓰여
**빈 응답(`''`)** 이 오고, 그것이 파싱 실패로 나타납니다.
`reasoning=False` 로 **2.5초**에 해결했습니다. (`num_predict=1500` 으로는 46초 쓰고도 실패)

### ★그런데 이 진단이 가능했던 이유는 «실패를 어떻게 세었는가» 입니다

```python
except Exception as exc:
    # 실패를 «OTHER» 로 뭉뚱그리지 않는다 — 그러면 모델 탓인지 파싱 탓인지 못 가른다
    return "_PARSE_FAIL", 0.0, type(exc).__name__
```

**만약 실패를 `OTHER` 로 처리했다면 「Ollama 라우터 정확도 0%」로 보고했을 겁니다.**
그러면 「2B 모델은 못 쓴다」는 **틀린 결론**에 도달했을 겁니다.

⇒ 11강이 말한 것과 같은 이야기입니다 —
*「tools 미호출이면 must 누락이 거의 따라온다. 따로 세면 같은 문제를 두 번 세는 셈이다」*
**원인이 다른 것을 한 칸에 넣으면 진단이 불가능해집니다.**

## ★★6-2. 시도 #2 — **eval 은 최고, 그런데 범위 밖이 무너졌습니다**

혼동 행렬이 지목한 SHIPPING 을 고쳤더니 **정확히 그곳이 올랐습니다.**

```
라우트          지침만   +fewshot    v2      변화
```

**그런데 `outscope` 가 78.8% → 57.6% 로 «폭락»했습니다.** 33건 중 14건을 더 놓쳤습니다.

### ★제가 «예측했던 함정»에 제가 빠졌습니다

`대회전략.md` §0 에 이렇게 써 두었습니다:
> 「라우터가 OTHER 를 덜 쓰게만 만들면 ① 지표는 «무조건» 오른다.

>  confidence 를 낮춰라.」

⇒ **outscope 를 같이 재지 않았다면 「macro F1 0.556 → 0.755, 큰 개선!」이라고 발표했을 겁니다.**
  실제로는 **서비스가 나빠졌습니다.**

### ★★그리고 — **제가 README 규칙을 어겼습니다**

> 「**한 번에 하나만 바꾸세요.** 둘을 동시에 바꾸면 올랐어도 «뭐 때문인지» 모릅니다.」

v2 는 ① SHIPPING 정의 강화 ② OTHER 억제 — **둘을 한꺼번에** 바꿨습니다.
그래서 **어느 쪽이 eval 을 올리고 어느 쪽이 outscope 를 무너뜨렸는지 모릅니다.**

⇒ 그래서 **v3 = SHIPPING 강화«만»** 을 따로 재는 중입니다(v2 에서 126자만 제거).

## ★★★6-3. 분리해 재보니 — **제 가설이 «기각»됐습니다**

```
                          eval    macro F1   outscope
v2 (SHIPPING + OTHER억제)  0.742    0.755     57.6%
v3 (SHIPPING «만»)        0.717    0.738     57.6%   ← ★똑같다
```

**outscope 가 «동일»합니다.** 폭락의 범인은 제가 지목한 「OTHER 억제」 문단이 **아니었습니다.**

### ★범인은 SHIPPING 강화 «안에» 숨어 있었습니다

v2·v3 에 **공통으로** 들어간 이 한 줄입니다:

> 「배송이 늦거나 멈췄다는 문의는 응대 범위 밖이 아니다.
>  **OTHER 로 보내지 말고** SHIPPING 이다.」

**「OTHER 로 보내지 말라」는 «금지»가 SHIPPING 문맥을 넘어
«전반적인 OTHER 억제»로 일반화된 것**으로 보입니다.

### ★★그래서 나온 교훈 — **「한 번에 하나만」은 프롬프트에서 어렵습니다**

코드라면 `CONF_THRESHOLD = 0.5 → 0.7` 처럼 **한 값만** 바꿀 수 있습니다.
프롬프트는 **문장**이라 **한 문장이 여러 효과를 냅니다.**

⇒ 제가 「하나만 바꿨다」고 믿은 **v3 도 실은 둘을 바꾸고 있었습니다.**
⇒ **분리 검증을 안 했다면 「OTHER 억제 문구를 빼면 해결된다」는 «틀린 처방»을 내놨을 겁니다.**

### ⇒ v4 — 같은 내용을 «금지»가 아니라 «포함»으로

```
전  「응대 범위 밖이 «아니다». OTHER 로 «보내지 말고» SHIPPING 이다」
후  「배송이 늦거나 멈췄다는 문의, 상태가 그대로라는 문의도 SHIPPING «에 든다»」
```
바뀐 것은 **이 한 줄뿐**입니다(1644자 → 1627자).

## ★★★6-4. 두 번째 가설도 «기각»됐습니다 — 범인은 「정의」가 아니라 「판단법」

v4 로 「OTHER 로 보내지 말고」를 「SHIPPING 에 든다」로 바꿨는데
**outscope 는 57.6% → 60.6%, 33건 중 «1건»만 회복**했습니다.

그래서 **범위 밖 문항이 «어디로» 가는지** 직접 추적했습니다.

```
                OTHER  SHIPPING  ORDER_PLACE  PRODUCT_INFO
v1 지침만         26       0          3            4
v4 SHIPPING강화   20       1          6            6
```

### ★**SHIPPING 으로 샌 건 «1건»뿐입니다.**

빠져나간 6건은 **ORDER_PLACE 3 · PRODUCT_INFO 3 · SHIPPING 1** 로 흩어졌습니다.
⇒ **SHIPPING 정의를 넓힌 것이 원인이 아닙니다.**

### 진짜 원인 — v4 에 남아 있는 **「판단법」**

> 「판단법: **"그래서 무엇을 알고 싶은가"** 가 배송비·배송기간·배송상태·배송방식이면 SHIPPING」

빠져나간 문항을 읽으면 드러납니다:

| 문항 | 간 곳 | 실제 |
|---|---|---|
| 「시착만 해보고 온라인에서 주문해도 되나요?」 | ORDER_PLACE | 매장 관련 = OTHER |
| 「백화점에도 입점되어 있는 브랜드인가요?」 | PRODUCT_INFO | 오프라인 = OTHER |
| 「블랙프라이데이 할인도 진행하시나요?」 | ORDER_PLACE | 행사 = OTHER |
| 「포장에 가격표가 붙어서 오나요?」 | PRODUCT_INFO | 배송 형태 아님 = OTHER |

⇒ ★**판단 기준을 정교하게 줄수록 모델은 «그 기준 안에서» 답을 찾으려 합니다.**
  **「해당 없음」이라는 답이 밀려납니다.**

### ★★그래서 두 개선의 «성격»이 다릅니다

```
fewshot 을 붙인다     eval +0.111 · outscope +6.0%p    ← 둘 다 오른다. «거래가 없다»
정의·판단법을 넓힌다   eval +0.185 · outscope -18.2%p   ← ★«거래»다
```

**예시를 주는 것은 공짜 점심이고, 기준을 넓히는 것은 거래입니다.**
어느 쪽을 감수할지는 12강 말대로 **«도메인»이 정합니다.**
잘못된 환불 안내가 금전 분쟁이 되는 이 도메인이라면, **범위 밖을 놓치는 쪽이 더 비쌉니다.**

## ★★★6-5. 마지막 — **두 효과가 «정확히» 더해집니다**

| 조합 | macro F1 | 변화 | outscope | 변화 |
|---|---|---|---|---|
| 지침만 | 0.556 | — | 78.8% | — |

| ★**v4 + fewshot** | **0.816** | **+0.260** | 66.7% | **−12.1%p** |

### ★outscope 가 «가산적»입니다 — **−18.2 + 6.0 = −12.2 ≈ −12.1**

그리고 fewshot 의 **+6%p** 는 **두 조건 모두에서 같은 크기**였습니다
(78.8→84.8 · 60.6→66.7). **한 번이 아니라 재현된 효과**입니다.

⇒ 두 변경은 **서로 다른 일을 하고, 간섭하지 않습니다.**
```
fewshot       «경계 사례를 보여준다»       → 양쪽 다 조금씩 올린다
정의·판단법     «네 라우트를 넓게 본다»      → eval 을 크게 올리고 범위 밖을 깎는다
```

### ★규칙 라우터(macro F1 0.677)를 넘은 것은

```
fewshot 만      0.667   ❌ 근소하게 못 넘음
v4             0.741   ✅
v4 + fewshot   0.816   ✅
```

⇒ **「LLM 이 규칙을 이기려면 지침을 고쳐야 했습니다.»** 갈아 끼우는 것만으로는 부족했습니다.

### ⇒ 그래서 «무엇을 고르나» — **도메인이 정합니다**

| 고른다면 | 이유 |
|---|---|
| **#1 fewshot 만** | **아무것도 희생하지 않는다.** 범위 밖을 놓치는 비용이 큰 도메인이면 이쪽 |
| **#5 v4+fewshot** | **점수가 가장 높다.** 대신 범위 밖 33건 중 4건을 더 놓친다 |

12강이 말한 그대로입니다 — *「두 축이 «반대로» 움직이는 교환 관계이고,
어느 쪽을 감수할지는 «도메인»이 정한다」*
**잘못된 환불 안내가 금전 분쟁이 되는 이 도메인이라면, 범위 밖을 놓치는 쪽이 더 비쌉니다.**
