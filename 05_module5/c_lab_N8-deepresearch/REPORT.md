## 1. 이 구조를 왜 쓰나 — 「구조가 «언제» 정해지는가」

지금까지 만든 것들과 이것의 차이는 **한 줄**이다.

```
라우팅       코드 짤 때 굳는다      if 유형=="환불": … 라고 쓰는 순간 갈래 확정
GraphRAG     인덱싱할 때 굳는다     질문이 도착하기 «전»에 그래프가 완성돼 있다
★이 구조     질문이 «온 뒤» 굳는다  목차·인원·배정이 질문마다 다르다
```

늦게 정할수록 질문에 잘 맞고, **늦게 정할수록 비싸다.**

⇒ 「에이전트가 워크플로보다 좋은가」에 답이 없는 이유가 여기 있다 —
**결정 시점이 다른 물건**을 좋고 나쁨으로 견주는 것이다.
옳은 질문은 **「이 문제에서 구조를 언제 굳혀도 되는가」**다.

**판단 기준 둘**
① 지금 갈래를 전부 적을 수 있나 → 적을 수 있으면 라우팅
② 같은 자료에 질문이 수천 번 들어오나 → 그러면 인덱싱해서 상각하는 쪽이 이긴다
**둘 다 아닐 때만** 이 구조를 꺼낸다.

## 3. ★컨텍스트 격리 — 이 구조의 심장

```python
def read_one(title, question, 지시):
    body = DOCS[title][:12000]      # ★원문이 이 함수 «안»으로 들어가고
    ...
    return ask(p, ...)              # ★요약 몇백 자만 나간다
```

원문은 조사관이 끝나는 순간 사라지고 **코디네이터는 그것을 본 적이 없다.**

```
격리 없으면  읽을 수 있는 양의 상한 = 창 «하나»
격리 하면    상한 = 창 × 조사관 수

★실측 격리율 1.4%   (코디가 본 글자 ÷ 팀이 읽은 글자)
```

**격리는 되돌릴 수 없다.** 조사관이 요약하며 빠뜨린 대목은 위층에서 복구할 방법이 없다.
그래서 요약 프롬프트에 **「쓸 것이 없으면 «관련 없음» 이라고만 답하라」**는 탈출구를 뒀다.
어설프게 요약하느니 빈손이 낫다 — **빈손은 로그에 보이지만 잘못된 요약은 안 보인다.**

## 4. 정한 것과 그 «대가»

| 결정 | 고른 것 | 포기한 것 |
|---|---|---|
| 코디에게 뭘 보여 주나 | 제목 + 앞 250자 카드 | 첫 문단이 대표성 없으면 무너짐 |
| 얼마나 넓게 나누나 | 4절 × 3건 | 가장 비쌈 · 중복률 상승 |
| 뭘 돌려받나 | 절 원고 + 인용 + 자기신고 | 절끼리 겹쳐도 아무도 모름 |
| 누가 「부족」이라 하나 | 조사관 자기신고 | 모델은 자기 일을 후하게 봄 |
| 뭘 재나 | 정답표 없는 5지표 | **글이 좋은지는 모름** |

★**「조건이 달라지면 다른 선택지가 맞는 답이 된다. 무엇을 포기했는지 알고 고르면 된다.」**

### 종료 조건은 «이중»으로

```python
if not 설정["재위임"] or wheel >= 설정["최대바퀴"] or not 빈칸:
```

모델의 판단만으로는 안 멈춘다 — 완벽을 요구받으면 언제까지고 「부족」이라 말할 수 있다.
예산만으로 멈추면 세 바퀴면 끝날 일을 늘 최대치까지 돌린다.
**둘을 함께 두면 보통은 내용이 멈추고 최악에는 예산이 멈춘다.**
그리고 **멈춘 이유를 상태에 남긴다**(`종료` 키) — 예산으로 멈춘 것과 충분해서 멈춘 것은
완전히 다른 사건인데, 로그에 안 남기면 구별할 수 없다.

```
조건              근거율        편중          중복률       안쓴   호출   자수
전부 켬(기준선)    72.3%±3.9    27.7%±1.5    33.3%±0.0   1.7    26   1752

구역 끔           73.5%±4.2    ★44.3%±8.6   42.9%±10.7  1.7    26   1986
역할 끔           75.6%±0.4    29.2%±2.3    33.3%±0.0   2.0    26   1749
```

### ① ★혼자서는 안 된다 — 이것이 제일 큰 결과

```
              팀        혼자      차이
근거율       72.3%     21.7%    ★3.3배
읽고 안 쓴    1.7건     7.0건    ★4배
호출          26회      14회     절반 (싸긴 하다)
```

±1.5 로 **안정적**이다. 혼자 하는 오케스트레이터는 **문서를 읽어 놓고 보고서에 못 쓴다.**
창 하나에 다 이고 쓰려니 앞 절만 쓰고 뒤가 빈다 — §2 ②가 그대로 나타난 자리다.

⇒ **「멀티 에이전트가 낫다」가 주장이 아니라 측정이 됐다.**

### ② ★근거율로는 장치를 «못 가른다»

```
조건 사이 최대 차이   3.3%p  (72.3 ~ 75.6)
회차 사이 폭          ±4%p
⇒ 차이가 잡음보다 «작다»
```

**이 지표는 이 실험의 계기가 아니다.** 구역을 꺼도 근거율이 안 내려간다 —
**구역은 낭비를 줄이는 장치지 품질을 올리는 장치가 아니다**는 뜻이다.

### ③ 갈리는 것은 둘

```
편중   «구역»이 가른다      27.7% → 44.3%  (+16.6%p)
       남의 구역을 안 알려 주면 조사관들이 같은 유명 문서로 몰린다
중복률 «배정»이 가른다      33.3% → 50.0%  (+16.7%p)
```

⚠ **강의는 「구역이 중복을 막는다」고 했는데, 우리 코퍼스에선 «배정»이 더 크게 갈랐다.**
32건이라 배정 하나가 차지하는 몫이 크다. **코퍼스 크기가 어느 장치가 일하는지를 바꾼다.**

## 7. 만들면서 겪은 것

### ★속도 제한은 «대기»가 아니라 «묶기»로 푼다

위키 수집이 429(Too Many Requests)로 **두 번 죽었다.** 지수 백오프를 붙였는데 또 죽었다.
**기다리는 법을 고치는 게 아니라 «치는 횟수»를 고쳐야 했다.**

```
링크    titles=A|B|C 로 묶어 20건씩   ✅ 통과
본문    ⛔묶을 수 없다 — MediaWiki 는 exlimit>1 일 때 «도입부»만 준다
        (묶어 보냈더니 첫 건만 오고 나머지가 «0자»로 와서 알았다)
        ⇒ 한 건씩 + 간격 + ★받는 즉시 캐시에 적어 중간에 죽어도 이어받기
```

### 인용이 0곳이던 일 — 프롬프트가 모호했다

첫 실행에서 **근거율 0.0%, 인용 0곳인 절 4개.** 메모에는 `«동학 농민 혁명»`이 제대로
있는데 원고에서 꺾쇠가 사라졌고, 한 절은 **리터럴 「문서명」**을 그대로 적어 올렸다.

```
전  "★근거가 있는 문장 끝에는 반드시 «문서명» 을 그대로 붙이세요."
후  쓸 수 있는 «실제 제목»을 목록으로 주고 + 예문 + 「한 절에 한 번만 붙이면 안 됩니다」
⇒ 근거율 0.0% → 16.0% → 75.0%
```

★**「그대로 붙이세요」가 모델에겐 「그 글자 그대로」였다.**

### 예산 3건인데 1건만 읽던 일

```python
if nxt in read: break      # ⛔고른 것이 이미 읽은 것이면 «통째로 멈췄다»
if nxt in read: continue   # ✅다음 후보를 집는다
```

로그의 「1건 읽고」를 눈으로 보고서야 알았다. **예산이 코드로 박혀 있어도
«도중에 끊기는 길»이 있으면 안 채운다.**
