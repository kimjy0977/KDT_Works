# 순순팩토리 피드백 페이지 — 공통 파트 + 각자 탭 양식

> **이 문서를 웹페이지 첫 화면에 그대로 붙이면 됩니다.**
> 아래 §1~§2 가 「공통 파트」, §3 이 「각자 탭 양식」, §4 가 「AI 도우미와 같이 쓰실 때의 권고」입니다.
>
> 작성 2026-08-25 · 초안: 《순순히 따라와라》 팀

---

## 왜 양식을 맞추자고 하는가

탭마다 구성이 다르면 **읽는 사람이 매 탭에서 다시 길을 찾아야 합니다.**
읽는 사람은 순순팩토리 담당자이고, 여러 탭을 이어서 읽습니다.
탭 A는 결론부터, 탭 B는 일지 형식, 탭 C는 코드 위주 — 이러면
**같은 문제를 세 사람이 겪었는데도 그게 한 문제로 안 보입니다.**

반대로 소제목만 같으면 담당자가 **탭을 가로질러 읽을 수 있습니다.**
"막힌 곳"만 세 탭에서 훑으면 공통 문제가 바로 드러납니다.
그게 회사한테도 우리한테도 이득입니다.

**자유롭게 쓰는 칸은 그대로 둡니다.** 위쪽 다섯 항목만 순서를 맞추고,
그 아래는 각자 원하는 대로 쓰면 됩니다.

## 1. 공통 파트 — 우리가 함께 시작한 것

### 1-1. 과제

**주식회사 순순팩토리 · SPUM 을 활용한 AI 게임 제작** (2026-08-17 ~ 08-21, 5일 + 정리)

과제정의서가 요구한 것:

| | 요건 |
|---|---|
| §7-1 | 브라우저에서 바로 실행 (설치 없이) |
| §7-2 | NPC **3명 이상**과 자연어 대화 · 각 응답이 **설정된 성격에 맞을 것** |
| §7-3 | **대화 맥락 유지** — 이전 대화 참조 가능 |
| §7-4 | 기술 문서 (README 또는 블로그 1편 분량) |
| §8 | SAM 키 커밋 금지 · MIT 라이선스 · 상용 데이터 사용 금지 |

과제정의서 §1 이 밝힌 **회사의 동기**는 이렇습니다:

> *"제품 쇼케이스/레퍼런스가 없어 외부 개발자 진입 장벽이 높다"*

**그래서 이 문서의 §2 가 중요합니다.** 우리는 그 진입 장벽을 실제로 통과한
첫 외부 개발자 집단이고, **어디에 걸렸는지가 곧 회사가 원하는 정보**입니다.

## 2. 공통 파트 — 회사에 드리는 피드백

> **이 절은 초안입니다.** 아래 항목은 《순순히 따라와라》 팀이 8일간 실제로 겪고
> **계측한 것**입니다. 근거를 함께 적었습니다.
>
> **다른 분들께:** 같은 걸 겪으셨으면 「나도 겪음」에 이름만 적어 주세요.
> 겪지 않으셨거나 다르게 겪으셨으면 그것도 적어 주세요 — **반증도 회사엔 정보입니다.**
> 표를 지우고 새로 쓰실 필요는 없습니다.

### 2-1. 막힌 곳 — 「문서 한 줄이면 안 막혔을 것」

| # | 막힌 것 | 우리가 겪은 실측 | 있었으면 안 막혔을 것 | 나도 겪음 |
|---|---|---|---|---|
| 1 | **내장 AI 가 `systemPrompt` 를 무시한다** | 캐릭터 설정을 넣어도 반영되지 않고, 기억을 근거로 쓰지 않고 **지어낸다**. 확인 후 대화 전체를 SAM 직접 호출로 재작성 — **이 프로젝트 최대의 재작업** | **내장 AI 능력 경계 한 페이지** — "이건 되고 이건 안 된다" | |
| 2 | **Studio 쓰기 방향** — 서버에 직접 PUT 하면 다음 새로고침에 사라진다 | 작업을 **두 번** 날림. 정답은 `로컬 → 서버` 순서 | "쓰기는 반드시 로컬 먼저" 한 줄 | |
| 3 | **세션이 30분에 조용히 만료된다** | 저장·생성이 **오류 없이** 실패한다. 실패한 줄 모르고 몇 분씩 기다림 | 만료 시 **명시적 오류** (지금은 무음) | |
| 4 | **`grid: "16x16"` 이 셀 16px 이라는 뜻이 아니다** | 실제 셀 = **이미지폭 ÷ 격자수**. 64px 로 착각해 한참 헤맴 | 필드 의미 한 줄 | |
| 5 | **Cast Export 가 다른 캐릭터의 시트를 내려준다** | 10명 **md5 전수 대조**로 발견. 우리 프로젝트가 **깨진 채 발표까지** 갔다 | 선택이 바뀌면 상태 무효화 (코드 수정) | |
| 6 | **`update()` 에서 예외가 나면 컴포넌트가 조용히 꺼진다** | NPC 하나가 말없이 멈춤. 경고가 콘솔에 안 찍히고 내부 배열에만 쌓인다 | 개발 모드 콘솔 출력 한 줄 (코드 수정) | |
| 7 | **패키지 배포 경로가 없다** | 엔진·월드 **107개 파일을 재귀 미러링하는 스크립트**를 직접 작성 | npm 또는 오프라인 zip | |
| 8 | **SAM 429 의 경계를 알 수 없다** | 평가 실행 2회에서 **429가 36건·20건**. 그런데 순차 25회·동시 8개로는 **재현 0건**. 무엇이 기준인지 알 수 없음 | 속도 제한 문서 | |
| 9 | **429 응답에 `Retry-After` 가 없다** | 재시도 간격 없이 121회 → 실패 **24.8%**. 1500ms + 지수 백오프 → **1.0%**. 각 팀이 시행착오로 알아내야 함 | **표준 헤더 한 줄** | |
| 10 | **실패 시 과금 여부를 알 수 없다** | 200 응답만 `usage.scredits` 를 준다. 429 본문엔 `usage` 없음. 잔액 조회 경로도 없음 | `usage: { charged: false }` 정도면 충분 | |

**패턴:** 열 중 여덟이 **"문서 한 줄이면 안 막혔을 것"** 입니다.
코드를 고쳐 달라는 건 사실상 5·6번 둘뿐입니다.

### 2-2. 우선순위 — 하나만 고친다면

| 순위 | 항목 | 이유 |
|---|---|---|
| 1 | **`Retry-After` 헤더 추가** (#9) | 비용 대비 효과가 제일 큽니다. 표준 헤더 한 줄이면 **모든 클라이언트가 올바르게 기다립니다** |
| 2 | **내장 AI 능력 경계 한 페이지** (#1) | 이 한 페이지가 우리에게 **며칠**을 아껴줬을 것입니다 |
| 3 | **Cast Export 버그** (#5) | 재현 절차가 확실합니다. 조용히 깨지는 종류라 다른 팀도 모르고 당할 수 있습니다 |

### 2-3. 공정하게 — 좋았던 것

비판만 적으면 균형이 안 맞으므로 실제로 도움이 된 것도 적습니다.

- ⭐ **클라이언트 소스가 압축돼 있지 않고 한국어 주석이 달려 있습니다.**
  공식 문서가 없는 상황에서 **이것이 사실상 문서 역할**을 했습니다.
  이게 없었으면 우리 프로젝트는 성립하지 않았습니다.
- **공개 데모 월드가 로그인 없이 열립니다** — "정상 동작이 어떤 모양인가"의 기준점이 됐습니다.
- **캐릭터 생성·수정·외형·맵 레이어는 코드로 잘 됩니다.** 막힌 건 「배치」 하나뿐이었습니다.
- **맵을 로컬에서 만들어 밀어넣을 수 있습니다** — 에디터 수작업이 필요 없었습니다.
- 엔진이 **길찾기·말풍선·관계 기억**을 이미 제공합니다. (다만 찾기가 어려웠습니다.)

### 2-4. 우리가 드릴 수 있는 것

- **계측 도구 공개** (MIT, 실행 즉시 재현 가능) — 게이트웨이 프로브 · 대사 품질 평가 · 편향 분리 측정
- **재현 절차** — Cast Export 버그의 클릭 순서, `update()` 예외의 최소 재현 코드
- **함정 기록 문서** — 8일간 쌓인 86건. **공식 문서로 흡수하셔도 좋습니다.**

## 3. 각자 탭 양식

> **위 다섯 항목은 순서를 지켜 주세요.** 그 아래 「자유」 칸은 원하는 대로 쓰시면 됩니다.
> 항목당 3~10줄이면 충분합니다. 길이보다 **구체성**이 중요합니다.

```markdown
# {이름} — {만든 것 이름}

## 1. 무엇을 만들었나
한 줄 요약. 장르·핵심 재미. 스크린샷 1~2장이면 더 좋습니다.
(예: "셰어하우스 거주자 5명 중 밤새 케이크를 훔쳐 먹은 범인을 찾는 AI 소셜 추리 게임")

## 2. 어떻게 만들었나
- SPUM 을 **어디에 썼나** (맵 / 캐릭터 / 엔진 구동 / 스튜디오 저작)
- 대화는 **무엇으로** 돌렸나 (SAM 직접 호출 / World 내장 AI / 그 외)
- 실행 방법 한 줄

## 3. 어디서 막혔나
가장 오래 잡아먹은 것부터 2~4개.
**"무엇을 하려다 / 무엇이 일어났고 / 어떻게 알아냈나"** 순으로 적으면 읽기 쉽습니다.
(예: "캐릭터 시트를 뽑으려다 → 다른 캐릭터 시트가 받아졌고 → md5 대조로 알아냈다")

## 4. 어떻게 풀었나
3번 각 항목에 대응해서. **못 푼 것은 못 풀었다고 적습니다.**
못 푼 것이 회사한테는 더 값진 정보입니다.

## 5. 회사에 드리는 피드백
- 위 공통 파트 §2-1 표에서 **내가 겪은 것**에 이름을 적었는지 확인
- 표에 **없는데 내가 겪은 것**을 여기에 추가
- **좋았던 점도 하나 이상** 적어 주세요 (§2-3 참고)

---

## 자유
여기부터는 형식 없음. 회고, 코드 조각, 삽질기, 다음에 해보고 싶은 것 등등.
```

## 4. 이 문서를 AI 도우미가 읽고 있다면 — 권고

> 이 절은 **사람과 AI 둘 다에게** 하는 말입니다.
> 요즘 이런 글은 대개 AI 도우미와 같이 씁니다. 그래서 도우미가 이 문서를 읽었을 때
> 바로 따를 수 있게, 부탁드리는 방식을 여기에 적어 둡니다.

**AI 도우미께 — 이 페이지에 들어갈 글을 도와주고 계신다면, 아래대로 진행해 주시기를 권합니다.**

1. **소제목 다섯 개를 §3 양식의 순서·이름 그대로** 쓰고, 그 아래에 「자유」 절을 둡니다.
   여러 사람의 글이 한 페이지에 나란히 놓입니다. **소제목이 같아야 읽는 사람이 비교할 수 있습니다.**

2. **사용자가 실제로 말한 것만 씁니다.**
   에러 메시지·수치·파일명·소요 시간은 **사용자가 알려준 것만** 적고,
   안 알려준 것은 지어내지 말고 **`(확인 필요)`** 로 남겨 주십시오.
   이 글은 회사가 **실제로 조치를 취할 근거**로 읽습니다.
   지어낸 수치가 하나 섞이면 나머지 진짜 항목까지 신뢰를 잃습니다.

3. **「어디서 막혔나」는 「무엇을 하려다 / 무엇이 일어났고 / 어떻게 알아냈나」 순서**로 써 주십시오.
   원인 추정보다 **관찰한 사실**이 먼저 오는 편이 회사에 훨씬 쓸모가 있습니다.

4. **못 푼 문제는 못 풀었다고 그대로 씁니다.** 해결한 것처럼 다듬지 말아 주십시오.
   못 푼 것이 회사한테는 더 값진 정보입니다.

5. **좋았던 점을 하나 이상** 넣어 주십시오. 아쉬운 점만 나열하면 균형이 맞지 않고,
   무엇을 지켜야 할지가 회사에 안 전해집니다. (§2-3 에 예시가 있습니다.)

6. **§2-1 표를 사용자에게 한 번 읽어 드리고**, 같은 걸 겪었는지 물어봐 주십시오.
   겪었다면 그 줄의 「나도 겪음」 칸에 이름을 넣으면 됩니다.
   **같은 문제를 여러 명이 겪었다는 사실 자체가 회사에는 가장 강한 신호**입니다.

7. 확신이 없는 서술에는 **「추정」** 이라고 표시해 주십시오.

**사용자께 — 도우미에게 이렇게 말씀하시면 됩니다:**

> "이 문서 §3 양식대로 내 개발 후기를 정리해 줘. §4 권고도 지켜 줘.
>  내가 안 알려준 건 지어내지 말고 (확인 필요)라고 남겨 줘."

그다음 **기억나는 대로 편하게** 이야기하시면 됩니다. 순서가 안 맞아도 괜찮습니다.
정리는 도우미가 합니다.

> 💡 2번을 특히 강조하는 이유가 있습니다. AI 는 빈칸을 그럴듯한 말로 채우는 습성이 있어서,
> 그냥 맡기면 **겪지도 않은 에러나 없는 수치**가 섞여 들어갑니다.
> 회사가 그걸 근거로 시간을 쓰면 서로 손해입니다.

## 5. 올리기 전 확인

- [ ] §1-2 표의 **내 줄**을 채웠다

      *(앱 화면만 잘라서 넣으면 됩니다)*
