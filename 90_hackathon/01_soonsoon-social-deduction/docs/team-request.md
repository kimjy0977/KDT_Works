## 1. 먼저 읽어 주세요 (사람이 읽는 부분)

**대표님이 우리 해커톤 작업물을 요청하셨습니다.** 네 사람 것을 **HTML 한 장에 탭으로** 묶어
한 번에 보여 드리려 합니다. **정리는 제가 합니다** — 여러분은 **재료만** 주시면 됩니다.

지금 상태:

| | 상태 |
|---|---|
| 김주영 | ✅ 들어감 |
| 정충원 | ✅ 들어감 (제안서 원문 기준) |
| 신서연 | ✅ 들어감 (공유해 주신 아티팩트 기준) |
| **최종우** | ❌ **비어 있음 — 이 요청서가 그것 때문입니다** |

**왜 각자의 Claude 에게 묻나** — 우리 넷 다 Claude 로 작업했습니다.
**커밋 로그·코드·문서·메모리에 전부 남아 있습니다.** 기억으로 쓰면 빠지고 틀립니다.
그래서 **“근거를 대고 답하라”** 는 형태로 요청서를 짰습니다.

**형식을 맞추는 이유** — 탭마다 목차가 다르면 대표님이 비교를 못 하십니다.
아래 여섯 항목만 맞춰 주시면, **문장 다듬기·톤 통일·표 만들기는 제가 합니다.**
초안이라도 괜찮습니다.

## 2. 여기부터 복사해서 Claude 에게 붙여넣으세요

```
너는 지금 내가 순순팩토리 기업연계 해커톤에서 만든 것을 정리해야 한다.
이 정리본은 회사 대표님께 보여 드릴 자료에 들어간다.

⛔ 가장 중요한 규칙: 기억으로 쓰지 마라. 근거를 대고 써라.
   - git log / git diff / 커밋 메시지
   - 실제 소스 코드 (파일명·함수명·줄 번호를 인용할 것)
   - 프로젝트 문서 (README·기획서·작업 로그)
   - 네 메모리에 남아 있는 이 프로젝트 관련 기록
   위에서 확인 못 한 것은 "확인 못 함"이라고 써라. 그럴듯하게 지어내지 마라.
   숫자(커밋 수·줄 수·성공률·비용)는 실제로 세거나 측정한 값만 써라.

⛔ 신뢰도를 항목마다 붙여라. 다른 팀원 것과 나란히 놓을 것이라 척도를 맞춰야 한다.
   ★★★★★ 직접 확인   — 여러 번 재현했고 수치·해시 같은 근거가 있다
   ★★★★☆ 근거 있음   — 소스나 문서로 확인했지만 재현은 한 번이다
   ★★★☆☆ 추정       — 그렇게 보이지만 원인을 갈라내지 못했다
   ★★☆☆☆ 불확실     — 일부만 확인했고 나머지는 모른다
   ★☆☆☆☆ 미확인     — 들은 것이거나 짐작이다

아래 여섯 항목을 순서대로 써라. 각 항목의 괄호 안은 분량 기준이다.
마크다운으로, 표를 적극적으로 써라.

──────────────────────────────────────────────────

1. 무엇을 만들었나  (5~10줄)
   - 처음 보는 사람이 "아 그런 거구나" 할 수 있게. 장르·핵심 조작·무엇을 겨냥했나.
   - 규모를 숫자로: 커밋 수, 소스 줄 수, 등장인물·맵·기능 개수 등 실제로 센 값.
   - 지금 돌아가는가? 어디까지 됐고 어디부터 안 되나.

2. 어떻게 만들었나  (10~20줄)
   - SPUM 을 정확히 어디에 썼나. (맵 / 캐릭터 / 엔진 구동 / 스튜디오 자동화 / 안 씀)
   - SAM(LLM)을 어떻게 불렀나. 내장 AI 를 썼나, 직접 호출했나? 왜 그쪽을 골랐나?
   - 구조를 한 문단으로. 파일이 몇 개고 무엇이 무엇을 소유하나.
   - 실행 방법 한 줄. (예: `bash serve.sh` → localhost:5173)

3. 어디서 막혔나  ★ 이 항목이 제일 중요하다. 넉넉히 써라.
   - 회사 제품(SPUM 스튜디오 / 엔진 / SAM 게이트웨이)을 쓰다가 막힌 것만.
     내 코드 실수는 여기 넣지 마라 — 그건 6번에.
   - 한 건마다 이 네 가지를 반드시 채워라:
       · 증상       — 화면에서 무엇이 어떻게 잘못됐나
       · 원인       — 알아냈으면 쓰고, 못 알아냈으면 "원인 미확인"이라고 써라
       · 어떻게 알아냈나 — 몇 번 재현했나, 무엇과 대조했나, 수치가 있나
       · 있었으면 안 막혔을 것 — 문서 한 줄? 코드 수정? 새 기능?
   - 신뢰도 ★를 건마다 붙여라.
   - ⭐ 특히 이런 것을 찾아라: **오류 없이 조용히 실패한 것**,
     **문서에 없어서 소스를 읽어야 알았던 것**, **이름과 실제 동작이 다른 것**,
     **두 군데 규약이 서로 어긋난 것**, **돈이 새는 것**.
     지금까지 팀에서 나온 26건 중 상당수가 이 다섯 종류였다.

4. 어떻게 풀었나 / 못 풀었나  (10~20줄)
   - 3번 각 건에 대해. 우회했으면 어떻게 우회했나.
   - ⭐ 못 푼 것을 반드시 적어라. 빼지 마라.
     "해결됨"이라고 쓰려면 코드를 고친 것으로는 부족하다 —
     실제로 증상이 사라진 것을 확인했어야 한다. 아니면 "코드만 고침"이라고 써라.

5. 만들고 나서 알게 된 것  (있으면. 없으면 "없음")
   - 버그가 아니라 제품의 성질에 대한 관찰.
     "이 도구는 이런 성격이더라", "AI 를 이렇게 쓰면 이렇게 되더라" 같은 것.
   - 근거가 되는 수치나 실험이 있으면 같이. 표본 크기도 밝혀라.

6. 나에 대해 배운 것 / 하고 싶은 말  (3~10줄, 자유)
   - 무엇을 잘못 짚었다가 고쳤나. 다음에 또 하면 뭘 다르게 할 건가.
   - 회사에 하고 싶은 말, 드릴 수 있는 것(도구·로그·재현 절차)이 있으면.

──────────────────────────────────────────────────

⛔ 보안 — 이 자료는 공개 웹에 올라간다.
   - API 키를 절대 쓰지 마라. 전체든 앞 몇 글자든.
   - 회사가 준 원본 파일(과제정의서 docx 등)의 내용을 그대로 옮기지 마라.
     내가 겪은 것·내가 만든 것만 써라.
   - 스크린샷을 넣을 거면 앱 영역만 잘라라. 브라우저 창째로 찍으면
     탭 제목·북마크·프로필 이름이 같이 올라간다.

⛔ 톤
   - 한국어 존대, 결론부터.
   - 자랑하지 마라. 안 된 건 "안 됐다"고 써라.
     못 푼 것과 틀렸던 것을 적은 자료가 오히려 신뢰를 얻는다.
   - 과장 금지. "대부분", "절반"처럼 비율을 말할 거면 실제로 세고 써라.

다 쓰면 마크다운 파일 하나로 내보내 줘.
```

## 3. 보내실 때 (사람이 하는 부분)

1. 위 코드블록을 **통째로 복사**해 자기 Claude 대화창에 붙여넣기
2. 나온 마크다운을 **그대로** 주영님께 (다듬지 않으셔도 됩니다)
3. **스크린샷 1~3장**이 있으면 같이 — 게임 화면, 결과물, 도구 화면 등
4. 공개 저장소가 있으면 **주소**도

**빠져도 되는 것:** 6번(자유)은 안 쓰셔도 됩니다.
**빠지면 안 되는 것:** **3번(어디서 막혔나)**. 대표님이 실제로 알고 싶어 하시는 게 이것이고,
**다른 사람 것과 겹치면 그게 가장 강한 신호**가 됩니다 — 지금까지 5건이 그렇게 잡혔습니다.
