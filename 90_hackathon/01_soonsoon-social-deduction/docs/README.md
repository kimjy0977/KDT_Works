# 문서 지도 — 무엇을 어디에 적는가

> 문서가 늘어나면서 같은 내용이 여러 곳에 흩어지기 시작했다. **기록 전에 이 표를 본다.**
> 새 사실을 알게 되면 **한 곳에만** 적고, 다른 문서에서는 링크로 가리킨다(SSoT).

| 파일 | 담는 것 | 담지 않는 것 |
|---|---|---|
| **`sam-connection-guide.md`** | **SPUM Studio · SAM 사용법 정본.** 화면 조작 절차 · localStorage 키 · 데이터 스키마 · API 연결 · 진단 체크리스트 | 코드 설계, 게임 기획 |
| **`engine-capability-audit.md`** | **`spum-engine` / `spum-world` 코드 역량.** 이 API 로 뭐가 되고 뭐가 안 되나, 소스에서 확인한 사실 | 화면 조작법(→ 사용법 파일) |
| **`work-rules.md`** | **함정과 재발방지 규칙.** 한 번 당한 것, 브라우저 자동화 요령, 검증 태도, git 규율 | 새 기능 설명, 스키마 |
| **`game-spec.md`** | **기획(하려는 것).** 규칙 · 캐릭터 · 루프 설계 | 구현 현황 (→ handoff) |
| **`handoff.md`** | **진행 현황과 세션 인계.** 지금 어디까지 왔나, 다음 시작점, 검증 결과 | 재사용 가능한 지식 (→ 위 3개) |
| **`tutorial.md`** | **공개 기술 문서(과제 산출물 §7-4).** 외부 개발자가 읽는 구현기 | 내부 사정, 미검증 추정 |
| **`spum-feedback.md`** | **회사(순순팩토리)에 전달할 제품 피드백.** 쓰다가 부딪힌 마찰·결함·제안 | 우리 코드 사정, 비난 |
| **`team-onboarding.md`** | **팀원 인수인계.** 환경 세팅 · SPUM 을 코드로 다루는 방식 · 함정 5개 요약 | 상세 스키마(→ sam-connection-guide) |
| **`multiplayer-design.md`** | **멀티플레이 설계안.** 규칙 엔진 계약 · 시야 필터링 · 위치 동기화 · 비용 상한 | 구현 현황(아직 없음), 싱글 기획(→ game-spec) |
| **`worklog.md`** | **작업 이력.** 무엇을 언제 왜 했나 | 사고 상세(경로·해시·노출값 금지) |
| **`../proto/DEPLOY.md`** | **배포 정본.** 왜 Vercel 인가 · 걸림돌 · 환경변수 · 순서 · 초대 코드 발급 | 게임 규칙, 코드 설계 |
| **`../CLAUDE.md`** | **세션 하네스.** 규율 · 읽는 순서 · 코드 지도 · 핵심 함정 요약 | 긴 설명 (요약 + 포인터만) |

## 판단이 애매할 때

| 이런 걸 알게 됐다 | 여기에 |
|---|---|
| "Studio 의 이 버튼은 이런 동작이더라" | `sam-connection-guide.md` |
| "이 엔진 API 는 이름과 달리 이런 것이더라" | `engine-capability-audit.md` |
| "이거 하다가 데였다. 다음엔 이렇게" | `work-rules.md` |
| "이 데이터의 구조는 이렇더라" | `sam-connection-guide.md` (스키마 절) |
| "이번에 이만큼 만들었고 이건 아직 안 됐다" | `handoff.md` |
| "외부에 이렇게 설명하면 좋겠다" | `tutorial.md` |
| "멀티로 가려면 이걸 먼저 정해야 한다" | `multiplayer-design.md` |
| "이건 SPUM 제품 문제다. 회사가 알아야 한다" | `spum-feedback.md` |
| "배포하려면 이게 필요하더라" | `../proto/DEPLOY.md` |

**중복이 생기면 정본을 하나 정하고 나머지는 지운다.** 값이 3곳 이상 흩어지면 드리프트가 시작된 것이다.
