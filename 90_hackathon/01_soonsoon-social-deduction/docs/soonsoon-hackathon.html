어디서 막혔나

  1. 내장 AI 로 게임을 굴리려 했는데 설정을 안 지켰다. 추리 게임은 “누가 무엇을 봤는가”가 사실이어야 성립하는데 지어내면 게임이 아닙니다. → 항목별 표를 만들어 하나씩 확인하고서야 알았습니다.
  2. 평가를 돌렸더니 “토론이 방해가 된다”는 결론이 나왔다. 실제로는 실패의 100% 가 429 였습니다. → 하마터면 틀린 결론을 회사에 낼 뻔했습니다.
  3. 캐릭터 하나가 서 있을 때도 걷는 애니메이션을 재생했다. Cast Export 가 다른 캐릭터의 시트를 내려준 것이었습니다. → 10명을 md5 전수 대조해서 발견했습니다.
  4. 8·10인 무대를 만들었는데 게임에는 6명만 나왔다. 맵도 방 10개, 인원 화면도 「10 / 10」인데 게임에만 6명이었습니다. → 실제로 플레이해 보고 알았습니다. 코드를 읽어선 안 보였습니다.

어디서 막혔나

스튜디오가 활발히 개발 중인 만큼 UI 가 자주 갱신되는데, 그때마다 DOM 선택자를 처음부터 다시 찾아야 했습니다. 개발 단계 제품에서는 자연스러운 일이지만, 자동화 측에서는 기능을 추가하는 시간보다 깨진 선택자를 복구하는 시간이 더 커지는 구조가 됩니다.

문제의 본질은 브라우저 자동화 자체가 아니라 「UI 표현에 의존할 수밖에 없다는 점」입니다.

그 밖에 계측으로 확인한 마찰 지점은 §4 표의 #2 · #3 · #4 · #7 · #9 · #11 · #14 입니다.

제안 — 3단계 점진안

§3-C 에 요약했습니다. 부담이 적은 순서로 정리했고, 1단계만 반영되어도 실무적으로는 큰 도움이 됩니다.

  • 1단계 — 핵심 요소에 data-testid + 자동화용 인증 수단 (반나절~1일)
  • 2단계 — 내부 API 사용 허가 + 최소 문서 (이미 있는 것에 대한 허가)
  • 3단계 — 공식 MCP 서버. 선언형(월드가 어떤 상태여야 하는가) 설계를 권장 — 중간에 실패해도 재적용으로 수렴하므로 에이전트 환경에서 안정적입니다
world_validate 의 중요성 “플레이 가능한 상태까지” 자동화하려면 에이전트가 스스로 결과를 검증할 수 있어야 합니다. 스폰 존재 · 경로 연결 · 엔티티가 충돌 타일 위에 있지 않은지를 반환해 주면 에이전트가 자체 수정 루프를 돌 수 있습니다. 이것이 있고 없고가 자동화 완성도를 크게 좌우합니다.

기여할 수 있는 것

  • 레퍼런스 구현 — 이미 공개돼 있습니다. MCP 가 제공되면 이 파이프라인의 하부를 MCP 호출로 교체한 클라이언트 측 레퍼런스와 실사용 예제를 정리해 드리겠습니다
  • 우선 검증 — 각 단계 반영 시 가장 먼저 테스트하고 재현 로그와 함께 피드백을 드리겠습니다
  • 도구 설계 협의 — 실제 사용 시나리오 기반으로 도구 시그니처와 스키마를 함께 다듬겠습니다
