> **이 문서는 팀 제안서에 합칠 초안이다.** 팀원(SPUM Kit)이 이미
> [스튜디오 외부 자동화 인터페이스 제안](https://spum-proposal.vercel.app)을 작성했다 —

>

> 형식은 그쪽 2-1 표(항목 / 실측 / 영향)를 그대로 따라 합치기 쉽게 했다.
>
> 작성 2026-08-24 · 근거는 전부 자체 계측. 도구 = `proto/tools/sam-probe.mjs` · `proto/tools/eval.mjs`

## A. SAM 게이트웨이 — 팀 제안서 2-1 표에 **없는 영역**

| 항목 | 실측 내용 | 영향 |
|---|---|---|
| **429 속도 제한이 문서에 없다** | 평가 하네스 실행 2회에서 `HTTP 429 RATE_LIMITED` **36건 / 20건** 발생. 그런데 **재현이 안 된다** — 순차 25회(300토큰)·동시 8개·실제 프롬프트(2919자) 10회 연속 모두 **429 0건** | 클라이언트가 **경계를 알 수 없다.** 안전한 호출 속도를 추측으로 정할 수밖에 없다 |
| **429 응답에 `Retry-After` 가 없다** | 응답 본문은 `{"ok":false,"error":{"code":"RATE_LIMITED","message":"API key rate limit exceeded"}}`. 속도제한 헤더(`Retry-After`·`X-RateLimit-*`) **없음** | **얼마나 기다려야 하는지 모른다.** 즉시 재시도하면 계속 맞고, 과하게 기다리면 느려진다 |
| **429는 즉시 재시도가 무용하다** | 재시도 간격 없이 121회 호출 → 최종 실패 **24.8%**. 호출 간격 1500ms + 지수 백오프 적용 → **1.0%** | 대응책은 있으나 **각 팀이 시행착오로 알아내야 한다** |
| **실패 시 과금 여부를 알 수 없다** | 200 응답만 `usage.scredits` 를 준다. 429 본문엔 `usage` 가 없다. 클라이언트가 확인할 잔액 조회 경로도 없음 | 팀원이 **504에서 크레딧 249 소모**를 확인했다(제안서 2-1). 429도 같은지 확인 불가 |
| **비용이 입력 길이에 크게 좌우된다** | 동일 모델·`max_tokens 300` 기준 — 짧은 프롬프트(20자) **2.13 SSAM** / 실제 게임 프롬프트(2,919자) **4.67 SSAM**. `max_tokens 8` 은 0.08 | **대화형 게임은 대화록이 길어질수록 비용이 가속**된다. 예측이 어렵다 |

### 요청 (A)

1. **속도 제한 값 공개** — 요청/분, 토큰/분, 동시 요청 중 무엇이 기준인지. 값 자체보다 **기준이 무엇인지**가 중요하다.
2. **`Retry-After` 헤더 추가** — 가장 비용이 낮으면서 효과가 큰 항목이다. 표준 헤더 한 줄이면 모든 클라이언트가 올바르게 기다린다.
3. **실패 응답에도 과금 여부 표기** — `usage: { charged: false }` 정도면 충분하다.
4. **비용 산정식 안내** — 입력/출력 토큰당 SSAM. 지금은 실측으로 역산해야 한다.

> ※ 1·2번은 **문서·헤더 작업**이라 부담이 작다고 판단한다. 팀원 제안서 1단계와 성격이 같다.

## B. SPUM Engine 패키지 배포 — 저작이 아니라 **런타임** 쪽

팀 제안서는 스튜디오(저작)를 다룬다. 우리는 `spum-engine`·`spum-world` 를 **직접 구동해** 게임을 만들었고, 그 과정에서 나온 것들이다.

| 항목 | 실측 내용 | 영향 |
|---|---|---|
| **패키지 배포 경로가 없다** | npm 등에 없어 `https://spum.soonsoon.ai/packages/...` 를 **재귀적으로 긁어 미러링**하는 스크립트를 자작했다(`mirror.mjs`). engine 70 + world 37 = 107 파일 | 버전 고정·재현 가능한 빌드가 안 된다. 팀마다 각자 미러링 도구를 만들게 된다 |
| **import 에 캐시 무력화 쿼리가 붙어 있다** | `./WorldAIState.js?v=world-assignment-drama-20260616-1` — 그대로 파일명으로 쓰면 **윈도우에서 `?` 를 못 써 저장 실패** | 미러링·오프라인 번들링이 깨진다. 쿼리를 떼는 처리를 각자 해야 한다 |
| **`BubbleRenderer` 가 루트에서 export 안 됨** | UI 3종 중 2종만 루트 `index.js` 에 노출. 말풍선은 `lib/domain/ui/index.js` 에서 직접 import 해야 찾는다 | 있는 기능을 **없는 줄 알고 직접 만들 뻔했다** |
| **`PathfindingManager.buildFromTileMap()` 이 기본 테마와 안 맞는다** | 타일 속성 `walkable` 을 읽는데 제공 테마에는 그 속성이 없다 | 길찾기를 쓰려면 `setGrid()` 로 직접 넘겨야 한다는 걸 소스를 읽고서야 알았다 |
| **`CameraController` 가 추적 카메라가 아니다** | 이름과 달리 마우스 줌/팬 전용. 따라가는 카메라는 직접 작성해야 했다 | 이름에서 오는 오해. 문서 한 줄로 해결된다 |
| ⭐ **`update()` 예외가 컴포넌트를 조용히 끈다** | `GameObject._executeUpdate` 가 `catch → c.enabled = false` 하고, 경고를 **`engine._frameWarnings` 에만** 담는다. **콘솔에 안 찍힌다** | **NPC 하나가 말없이 멈추는데 원인을 못 찾는다.** 우리는 이걸 찾는 데 상당한 시간을 썼다. 디버깅 경험에서 가장 큰 함정이었다 |

### 요청 (B)

1. ⭐ **`update()` 예외를 콘솔에 한 번은 찍어달라** — 또는 개발 모드 플래그. **B 항목 중 이것 하나가 체감 개선이 가장 크다.**
2. **패키지 배포**(npm 또는 버전 고정 CDN) — 어려우면 **오프라인 번들 zip** 제공만으로도 충분하다.
3. import 쿼리스트링 제거 또는 미러링 가이드 한 줄.
4. 루트 `index.js` export 정리 + "이름과 다른 것" 목록(예: `CameraController`).

## C. AI NPC 품질 — 회사 제품의 **핵심 가치**에 직결되는 발견

SPUM CG(Concept Generating) 태그로 캐릭터를 만들고 SAM 으로 말을 시키는 것이 제품의 방향이라면, 아래는 그 조합에서 실제로 나온 현상이다. **AI 소셜 추리 게임 6판을 자동 실행해 계측**했다(`tools/eval.mjs`).

| 항목 | 실측 | 의미 |
|---|---|---|
| **프롬프트 지시 미준수** | "한 문장, 길어도 두 문장" 을 명시했는데 **63.8% 가 위반** | 길이·형식은 **프롬프트로 보장되지 않는다.** 코드로 자를 수밖에 없었다 |
| **되풀이** | 앞사람과 사실상 같은 말을 하려는 시도 **21.7%** | 후처리 필터(글자 2-gram 55%)를 붙여 통과율 **1.7%** 로 낮췄다. 필터 없으면 대화가 무너진다 |
| ⭐ **캐릭터 성격이 곧 AI의 편향이 된다** | 6판 17표 중 **76%가 두 캐릭터에 고정**. 마피아가 누구인지와 **무관**했다.<br>「활발·통금 어김」 7표 · 「새침·깔끔」 6표 · 「먹보·눈치 없는」 3표 · **「졸림·느긋」 1표**<br>졸린 캐릭터는 **6판 중 2판에서 마피아였는데도 1표**를 받았다 | **AI 들은 대화 내용이 아니라 성격 묘사로 판단한다.** 결과적으로 지목 적중률이 무작위(33.3%)보다 낮은 **11.8%** 가 나왔다 |

### 왜 이것이 순순팩토리에 중요한가

**SPUM CG 태그는 캐릭터의 외형만 정하는 것이 아니라, 그 캐릭터가 AI 상호작용에서 어떤 취급을 받을지까지 정한다.**

- "험상궂은" 태그를 단 NPC 는 **다른 AI 들에게 상시 의심받는다.**
- "느긋한" 태그를 단 NPC 는 **사실상 투명인간이 된다.**
- 제작자는 외형을 고른다고 생각하지만 실제로는 **게임 밸런스를 고르고 있다.**

이건 버그가 아니라 **LLM 의 성질**이다. 다만 태그 기반 캐릭터 생성을 파는 제품이라면 **알고 파는 것과 모르고 파는 것이 다르다.**

### 제안 (C)

1. **CG 태그별 「AI 인식 편향」 데이터** — 회사가 태그 카탈로그를 갖고 있으므로, 태그 조합이 LLM 상호작용에서 어떻게 인식되는지 계측할 수 있는 유일한 주체다. 이건 **경쟁사가 못 만드는 자산**이다.
2. **캐릭터 생성 시 힌트** — "이 태그 조합은 다른 AI 에게 의심받기 쉽습니다" 수준이면 충분하다.
3. 우리가 만든 **평가 하네스를 공유**하겠다. 대사 품질(되풀이·지시 준수·길이)과 지목 편향을 SAM 호출만으로 잰다. 브라우저 불필요.

## E. 2차에서 우리가 하고 싶은 것 (팀 논의용 초안)

팀원은 **「SPUM을 Claude Code에서 자연어로 제작」**(저작 자동화)을 제안했다. 우리는 그 **다음 단계**를 맡는 것이 자연스럽다고 본다.

> **저작이 자동화되면, 그다음 질문은 "만들어진 게 재미있는가"다.**

- **1안 — AI NPC 품질 계측 도구를 제품화.** 위 C 를 일반화해서, SPUM 으로 만든 월드의 NPC 대화 품질을 자동으로 재는 도구. 제작자가 "내 NPC 가 설정대로 말하는가"를 배포 전에 확인할 수 있다.
- **2안 — 사람 + AI 혼합 멀티플레이.** 같은 방에 사람과 AI 가 섞여 서로를 구분하지 못하는 소셜 게임. 설계안은 이미 작성했다(`docs/multiplayer-design.md`). SPUM 의 캐릭터·월드 자산이 그대로 쓰인다.
- **3안 — CG 태그 ↔ LLM 인식 매핑 연구.** C-1 을 회사와 공동으로. 결과는 회사의 자산이 되고, 우리는 사례를 얻는다.

**우선순위는 팀 논의로 정한다.** 다만 세 안 모두 **팀원의 저작 자동화가 전제**라 순서가 자연스럽다.
