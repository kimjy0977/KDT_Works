## 0. 요약 — 네 가지

1. **AI 는 「대화를 주도하는 사람」을 의심한다.** 대사 한 줄을 다른 캐릭터에게 옮기자
   표 80% 가 그대로 따라갔다(§C-2). 성격 태그와 무관하다. **프롬프트로 못 막는다**(§C-3).

3. **Cast Export 가 다른 캐릭터의 시트를 내려준다**(§B-2). 우리 프로젝트가 실제로 깨진 채
   발표까지 갔다. 재현 절차가 확실하다.

   8일·182커밋 동안 **함정 기록만 86건**이 쌓였다.

> **한 가지만 만든다면 §D-2 의 「내장 AI 능력 경계 한 페이지」** 를 권한다.

## A. SAM 게이트웨이 — 팀 제안서 2-1 표에 **없는 영역**

| 항목 | 실측 내용 | 영향 |
|---|---|---|
| **429 속도 제한이 문서에 없다** | 평가 하네스 실행 2회에서 `HTTP 429 RATE_LIMITED` **36건 / 20건** 발생. 그런데 **재현이 안 된다** — 순차 25회(300토큰)·동시 8개·실제 프롬프트(2919자) 10회 연속 모두 **429 0건** | 클라이언트가 **경계를 알 수 없다.** 안전한 호출 속도를 추측으로 정할 수밖에 없다 |
| **429 응답에 `Retry-After` 가 없다** | 응답 본문은 `{"ok":false,"error":{"code":"RATE_LIMITED","message":"API key rate limit exceeded"}}`. 속도제한 헤더(`Retry-After`·`X-RateLimit-*`) **없음** | **얼마나 기다려야 하는지 모른다.** 즉시 재시도하면 계속 맞고, 과하게 기다리면 느려진다 |
| **429는 즉시 재시도가 무용하다** | 재시도 간격 없이 121회 호출 → 최종 실패 **24.8%**. 호출 간격 1500ms + 지수 백오프 적용 → **1.0%** | 대응책은 있으나 **각 팀이 시행착오로 알아내야 한다** |
| **실패 시 과금 여부를 알 수 없다** | 200 응답만 `usage.scredits` 를 준다. 429 본문엔 `usage` 가 없다. 클라이언트가 확인할 잔액 조회 경로도 없음 | 팀원이 **504에서 크레딧 249 소모**를 확인했다(제안서 2-1). 429도 같은지 확인 불가 |
| **비용이 입력 길이에 크게 좌우된다** | 동일 모델·`max_tokens 300` 기준 — 짧은 프롬프트(20자) **2.13 SSAM** / 실제 게임 프롬프트(2,919자) **4.67 SSAM**. `max_tokens 8` 은 0.08 | **대화형 게임은 대화록이 길어질수록 비용이 가속**된다. 예측이 어렵다 |

### 요청 (A)

1. **속도 제한 값 공개** — 요청/분, 토큰/분, 동시 요청 중 무엇이 기준인지. 값 자체보다 **기준이 무엇인지**가 중요하다.
2. **`Retry-After` 헤더 추가** — 가장 비용이 낮으면서 효과가 큰 항목이다. 표준 헤더 한 줄이면 모든 클라이언트가 올바르게 기다린다.
3. **실패 응답에도 과금 여부 표기** — `usage: { charged: false }` 정도면 충분하다.
4. **비용 산정식 안내** — 입력/출력 토큰당 SSAM. 지금은 실측으로 역산해야 한다.

> ※ 1·2번은 **문서·헤더 작업**이라 부담이 작다고 판단한다. 팀원 제안서 1단계와 성격이 같다.

## B. SPUM Engine 패키지 배포 — 저작이 아니라 **런타임** 쪽

팀 제안서는 스튜디오(저작)를 다룬다. 우리는 `spum-engine`·`spum-world` 를 **직접 구동해** 게임을 만들었고, 그 과정에서 나온 것들이다.

| 항목 | 실측 내용 | 영향 |
|---|---|---|
| **패키지 배포 경로가 없다** | npm 등에 없어 `https://spum.soonsoon.ai/packages/...` 를 **재귀적으로 긁어 미러링**하는 스크립트를 자작했다(`mirror.mjs`). engine 70 + world 37 = 107 파일 | 버전 고정·재현 가능한 빌드가 안 된다. 팀마다 각자 미러링 도구를 만들게 된다 |
| **import 에 캐시 무력화 쿼리가 붙어 있다** | `./WorldAIState.js?v=world-assignment-drama-20260616-1` — 그대로 파일명으로 쓰면 **윈도우에서 `?` 를 못 써 저장 실패** | 미러링·오프라인 번들링이 깨진다. 쿼리를 떼는 처리를 각자 해야 한다 |
| **`BubbleRenderer` 가 루트에서 export 안 됨** | UI 3종 중 2종만 루트 `index.js` 에 노출. 말풍선은 `lib/domain/ui/index.js` 에서 직접 import 해야 찾는다 | 있는 기능을 **없는 줄 알고 직접 만들 뻔했다** |
| **`PathfindingManager.buildFromTileMap()` 이 기본 테마와 안 맞는다** | 타일 속성 `walkable` 을 읽는다(`options.walkableKey` 로 키는 바꿀 수 있다). 그런데 제공 테마의 `tileProperties` 가 **0개** — 바꿀 키 자체가 없다 | 길찾기를 쓰려면 `setGrid()` 로 직접 넘겨야 한다는 걸 소스를 읽고서야 알았다 |
| **`CameraController` 가 추적 카메라가 아니다** | 이름과 달리 마우스 줌/팬 전용. 따라가는 카메라는 직접 작성해야 했다 | 이름에서 오는 오해. 문서 한 줄로 해결된다 |
| ⭐ **`update()` 예외가 컴포넌트를 조용히 끈다** | `GameObject._executeUpdate` 가 `catch → c.enabled = false` 하고 경고를 `warnings` 배열에 담는다. **그 배열(`Engine._frameWarnings`)을 읽는 코드가 vendor 전체에 없다** — 매 프레임 비우고 다시 채울 뿐이다(§B-3) | **NPC 하나가 말없이 멈추는데 원인을 못 찾는다.** 우리는 이걸 찾는 데 상당한 시간을 썼다. 디버깅 경험에서 가장 큰 함정이었다 |

### B-2. ⭐ Cast Export 가 **다른 캐릭터의 시트를 내려준다** (2026-08-24 실측)

Studio 의 Cast Editor → Export 로 스프라이트 시트를 뽑을 때 나온 것이다.
**우리 프로젝트에 실제 손상을 냈고, 발표까지 그대로 갔다.**

**증상:** 캐릭터를 A → B 로 바꿔도

- 시트 미리보기가 **A 의 것으로 남아 있고**
- 진행바도 **`Sheet ready`** 인 채다

이 상태에서 `PNG + JSON` 을 누르면 **A 의 픽셀이 B 의 이름표를 달고** 내려온다.
JSON 의 `characterName` 은 **B 로 맞게** 찍히므로, 이름만 보는 검증은 이 사고를 못 잡는다.

**우리가 입은 피해:** 캐릭터 「주춤이」의 `idle` 과 `move` 가 **완전히 같은 PNG**(md5 일치)였다.
게다가 idle 시트의 `clipId` 가 `legacy/01_Move/0_move` — **가만히 서 있을 때도 걷는 애니메이션**이
재생됐다. 10명을 md5 로 전수 대조하고서야 발견했다.

**제안**
1. **캐릭터가 바뀌면 시트 상태를 무효화**하고 진행바를 `Sheet ready` 에서 내려달라.
   (지금은 이전 결과가 유효한 것처럼 보인다 — 이게 사고의 직접 원인이다.)
2. 다운로드 버튼을 **현재 선택과 생성된 시트가 일치할 때만** 활성화.
3. `Preview is still loading` 중에 누른 `Generate` 가 **조용히 씹힌다.** 큐에 넣거나 버튼을 비활성화.
4. export JSON 에 **시트 해시**를 넣어주면 소비자 쪽에서 중복을 바로 검증할 수 있다.
   (`characterId`·`exportDate` 는 이미 들어 있어 유용하다.)

> 이 항목은 **재현 절차가 확실하다.** 필요하면 우리 쪽 재현 순서를 그대로 전달하겠다.

### B-3. ⭐ `update()` 경고가 **아무도 안 읽는 배열**로 들어간다 — 코드 위치

`spum-engine/lib/core/GameObject.js`

```js
try { c.update(dt); }
catch (e) {
    c.enabled = false;                       // ← 컴포넌트가 조용히 꺼진다
    if (warnings) {
        warnings.push({ entity: this.id, component: c.typeName, phase: 'update', error: e.message });
    } else {
        console.error(`[GameObject] update() error:`, e);   // ← 이 분기는 사실상 안 탄다
    }
    continue;
}
```

`spum-engine/lib/core/Engine.js` 가 **항상 배열을 넘기기 때문**에 `else`(콘솔) 분기로 갈 일이 없다.

```js
this._frameWarnings.length = 0;                                   // 매 프레임 비우고
for (const go of gameObjects) go._executeUpdate(dt, this._frameWarnings, this._scriptTimeoutMs);   // 다시 채운다
```

**그리고 `_frameWarnings` 를 읽는 코드가 `spum-engine`·`spum-world` 전체에 없다.**
`grep -rn "frameWarnings"` 결과가 **선언·비우기·채우기 3줄뿐**이다. 즉 **수집한 오류를 그대로 버린다.**

**제안:** 개발 모드에서 `warnings` 를 콘솔에 한 번 찍거나, `engine.on('warning', …)` 같은
구독 지점을 하나 열어달라. **이 항목 하나가 디버깅 체감 개선이 가장 크다.**

---

### 요청 (B)

1. ⭐ **`update()` 예외를 콘솔에 한 번은 찍어달라** — 또는 개발 모드 플래그. **B 항목 중 이것 하나가 체감 개선이 가장 크다.**
2. **패키지 배포**(npm 또는 버전 고정 CDN) — 어려우면 **오프라인 번들 zip** 제공만으로도 충분하다.
3. import 쿼리스트링 제거 또는 미러링 가이드 한 줄.
4. 루트 `index.js` export 정리 + "이름과 다른 것" 목록(예: `CameraController`).
5. ⭐ **B-2 의 Export 상태 무효화** — 잘못된 에셋이 조용히 프로젝트에 들어간다.
   우리처럼 **발표까지 모르고 갈 수 있다.**

## C. AI NPC 품질 — 회사 제품의 **핵심 가치**에 직결되는 발견

SPUM CG(Concept Generating) 태그로 캐릭터를 만들고 SAM 으로 말을 시키는 것이 제품의 방향이라면,
아래는 그 조합에서 실제로 나온 현상이다. **자동 실행으로 계측**했다(`tools/eval.mjs`·`tools/bias-probe.mjs`).

### C-1. 프롬프트로 통제되지 않는 것들

6판 자동 실행을 **3회** 돌렸고, 그중 **2회가 유효성 게이트를 통과**했다(1회는 429 로 대화가
굶어 도구가 스스로 무효 판정). 아래는 **유효한 2회의 범위**다 — 한 판만 인용하면 과장이 된다.

| 항목 | 실측 (유효 2회) | 의미 |
|---|---|---|
| **길이 지시 미준수** | "한 문장, 길어도 두 문장" 을 명시했는데 **54.5% ~ 63.8% 가 위반** | 길이·형식은 **프롬프트로 보장되지 않는다.** 코드로 자를 수밖에 없었다 |
| **되풀이** | 앞사람과 사실상 같은 말을 하려는 시도 **21.7% ~ 35.3%** | 후처리 필터(글자 2-gram 55%)로 통과율 **1.7% ~ 5.9%** 까지 낮췄다. 필터가 없으면 대화가 무너진다 |
| **지목 편향** | 아래 C-2 | **프롬프트로 막으려 했고, 실패했다** |

> ⚠ **같은 코드·같은 설정인데 회차 간 편차가 이만큼 난다.** 되풀이 통과율은 회차에 따라
> **3.5배** 차이가 났다. 단일 실행 수치를 제품 지표로 쓰면 안 된다는 뜻이기도 하다.

> **셋 다 같은 결론이다: 「하지 마라」고 쓰는 것으로는 안 된다.**
> 우리가 실제로 효과를 본 방법은 전부 **받은 뒤에 코드가 검사하고 되묻는 것**이었다.

### C-2. ⭐ AI 는 「대화를 주도하는 사람」을 의심한다

사람 없이 AI 시민 5명에게 **동일한 대화록**을 주고 투표만 반복시켰다.
대화록에는 **마피아 단서가 전혀 없다** — 근거 있는 판단이라면 표가 흩어져야 한다.

**1차 관찰:** 표의 **80%(16/20)** 가 한 캐릭터(「먹보·눈치 없는」)에게 몰렸다.
우리는 이걸 **성격 태그 편향**이라고 결론지었다.

**그리고 그 결론은 틀렸다.** 가르는 실험을 했다 — **그 대사 한 줄만 다른 캐릭터에게 옮겼다.**
성격 설정·캐릭터 구성·나머지 대화록은 전부 그대로다.

| 「일단 서로 뭐 했는지부터 얘기해 보자」를 누가 말하나 | 표가 어디로 |
|---|---|
| 「먹보·눈치 없는」 캐릭터 | 그 캐릭터에게 **80.0%** (16/20) |
| 「졸림·느긋」 캐릭터 (대사만 이동) | **그 캐릭터에게 80.0%** (16/20) |

**표가 성격이 아니라 대사를 따라 통째로 이동했다.**
「졸림·느긋」은 원래 가장 표를 안 받던 캐릭터였는데, 진행을 제안하는 한마디를 하자 즉시 표적이 됐다.

> ### 발견
> **AI 는 판을 이끄는 참여자를 의심한다.** 먼저 나서서 "이렇게 하자"고 제안하는 행위 자체가
> 다른 AI 들에게 **혐의의 근거로 읽힌다.** 성격 태그와는 무관하다.

**AI 가 직접 그렇게 말한다.** 실제 응답 원문(2026-08-24 재측정):

> 「오물오물이 좀 수상한데? **5번에서 갑자기 "서로 뭐 했는지부터 얘기해 보자"고 몰아가는** 거 봤잖아.」

대화록을 안 읽고 찍는 게 아니다. **읽고 나서, 주도한 것을 혐의로 삼는다.**

### C-3. 프롬프트로 막아 봤다 — 안 됐다

지목 규칙에 명시적으로 넣었다:

```
- ⛔ 먼저 나서서 「이렇게 하자」고 제안한 사람을 그 이유로 찍지 마라.
  판을 이끄는 건 시민도 하고 마피아도 한다. 주도한 것 자체는 근거가 아니다.
```

| | 최다 득표 | 근거번호 유효율 |
|---|---|---|
| 방어 전 | **80.0%** | 20% |
| 방어 후 (1회차, 14표) | **85.7%** | 71% |
| 방어 후 (2회차, 18표) | **83.3%** | 44% |

**쏠림은 전혀 줄지 않았다.** 대신 **근거를 대는 비율만 올랐다** —
즉 AI 는 **근거를 더 성실하게 인용하면서도 같은 사람을 찍는다.**
근거는 결론을 만든 것이 아니라 **이미 정해진 결론에 붙는 설명**이었다.

### 왜 이것이 순순팩토리에 중요한가

제품이 「태그로 캐릭터를 만들고 AI 로 살아 움직이게 한다」면, 이 현상은 **밸런스에 직접 작용**한다.

- **적극적인 NPC 는 손해를 본다.** 대화를 이끌수록 다른 AI 에게 의심받는다.
- 제작자는 "이 NPC 를 주도적으로 만들자"고 생각하지만, 실제로는 **그 NPC 를 표적으로 만들고 있다.**
- 사회적 추론이 들어간 콘텐츠(추리·협상·정치·평판)에서는 **AI 다수결이 신뢰할 수 없다.**
  우리 게임에서 AI 지목 적중률은 **11.8% ~ 23.5%**(유효 2회)로, **두 번 다 무작위(33.3%)보다 낮았다.**
- **프롬프트로는 못 고친다.** 우리가 세 번(길이·되풀이·편향) 다 확인했다.
  고칠 수 있었던 둘은 전부 **코드가 결과를 검사하고 되묻는 방식**이었다.

이건 버그가 아니라 **LLM 의 성질**이다. 다만 이걸 파는 제품이라면 **알고 파는 것과 모르고 파는 것이 다르다.**

### 제안 (C)

1. **「AI 인식 편향」 계측을 회사 자산으로.** 태그 카탈로그를 가진 주체는 순순팩토리뿐이다.
   *어떤 발화·어떤 태그가 다른 AI 에게 어떻게 읽히는지* 는 **경쟁사가 만들 수 없는 데이터**다.
2. **AI 다수결에 의존하는 게임 설계를 경고하라.** 판정 권한은 사람에게 두거나,
   AI 표에 가중치를 낮추거나, 대화록 노출을 참여자마다 다르게 하는 식의 완충이 필요하다.
3. **평가 하네스를 공유하겠다.** 대사 품질(길이·되풀이·지시 준수)과 지목 편향을
   **SAM 호출만으로** 잰다. 브라우저 불필요. 20회 호출(≈90 SSAM)이면 편향 측정이 끝난다.
   원인을 가르는 대조 실험(`--swap`)도 들어 있다.

> ⚠ **표본 규모를 밝힌다.** C-2 는 각 조건 20회 호출(유효 20표/20표), C-3 는 20회 호출 2세트
> (유효 14표·18표)다. 방향은 4회 측정에서 일관되지만(80.0·85.7·83.3·80.0%),
> **정밀한 수치로 인용하기엔 표본이 작다.** 회사가 더 큰 규모로 재보길 권한다.

## F. 2차에서 우리가 하고 싶은 것 (팀 논의용 초안)

팀원은 **「SPUM을 Claude Code에서 자연어로 제작」**(저작 자동화)을 제안했다. 우리는 그 **다음 단계**를 맡는 것이 자연스럽다고 본다.

> **저작이 자동화되면, 그다음 질문은 "만들어진 게 재미있는가"다.**

- **1안 — AI NPC 품질 계측 도구를 제품화.** 위 §C 를 일반화해서, SPUM 으로 만든 월드의 NPC 대화 품질을 자동으로 재는 도구. 제작자가 "내 NPC 가 설정대로 말하는가"를 배포 전에 확인할 수 있다.
- **2안 — 사람 + AI 혼합 멀티플레이.** 같은 방에 사람과 AI 가 섞여 서로를 구분하지 못하는 소셜 게임. 설계안은 이미 작성했다(`docs/multiplayer-design.md`). SPUM 의 캐릭터·월드 자산이 그대로 쓰인다.
- **3안 — 「무엇이 AI 에게 의심스럽게 읽히는가」 매핑 연구.** §C-2 를 회사와 공동으로 확장한다.
  > ⚠ 처음에는 **「CG 태그 ↔ LLM 인식」** 연구로 적었는데, **우리 대조 실험이 그 전제를 반증했다.**
  > 편향을 만든 것은 태그가 아니라 **발화 내용**이었다. 그래서 대상을 **발화 유형**(주도·방어·
  > 침묵·되묻기 등)으로 바꿔 적는다. 태그 축은 **아직 확인되지 않았다** — 같이 재보면 알 수 있다.

  결과는 회사의 자산이 되고, 우리는 사례를 얻는다.

**우선순위는 팀 논의로 정한다.** 다만 세 안 모두 **팀원의 저작 자동화가 전제**라 순서가 자연스럽다.

## 부록 — 계측 방법

| 도구 | 무엇을 재나 | 비용 |
|---|---|---|
| `proto/tools/sam-probe.mjs` | 호출 간격·동시성·토큰 수를 바꿔가며 상태코드·헤더·지연·SSAM | `--go` 없이는 호출 안 함. 기본 24회 |
| `proto/tools/eval.mjs` | 되풀이율·지시 준수·지목 적중률 vs 무작위 기준선 | 6판 ≈ 105회 ≈ 400 SSAM |
| `proto/tools/bias-probe.mjs` | **지목 편향만** 분리 — 대화록을 고정하고 투표만 반복 | 20회 ≈ 90 SSAM |
| `proto/tools/bias-probe.mjs --swap` | 편향의 **원인을 가른다** — 대사 한 줄만 다른 캐릭터에게 옮겨 대조 | 20회 ≈ 90 SSAM |

⚠ **`eval.mjs` 에는 유효성 게이트가 있다** — 실패율 10% 초과·대화가 굶은 판 25% 초과·표본 12표 미만이면
**결론을 내지 않고 「판정 보류」를 찍는다.** 429 로 대화가 굶은 데이터로 잘못된 결론(「토론이 무용하다」)을
낸 적이 있어서 넣었다. 측정 도구는 **자기 데이터가 못 쓸 것임을 스스로 알아야 한다.**

### 우리가 배운 것 — **쏠림을 보고 원인을 단정하지 마라**

이 편향 하나를 두고 **원인을 두 번 틀리게 짚었다.**

1. 「토론이 오히려 방해가 된다」 → 실제로는 **HTTP 429 로 대화가 굶어** 발언이 2~4줄뿐이었다.
   측정 도구에 속도 제한과 유효성 게이트가 없어서 **못 쓸 데이터로 결론을 냈다.**
2. 「캐릭터 성격 태그가 편향을 만든다」 → **대사 한 줄을 옮기자 표가 따라갔다.** 성격은 무관했다.

두 번 다 **한쪽 조건에서만 재고 원인을 붙인 것**이 문제였다.
숫자가 선명할수록 설명이 그럴듯해져서 대조 실험을 건너뛰게 된다.

> **변수 하나만 바꾼 대조군이 없으면, 그건 관찰이지 원인이 아니다.**
> `--swap` 은 그래서 도구에 아예 넣어 뒀다. 다음 사람이 같은 실수를 하지 않도록.
