## A. SPUM Studio 조작

**A-1. 쓰기 방향은 반드시 `로컬 → 서버`**
```js
window.spumStudioData.export();                    // ① 백업 먼저 (항상)
localStorage.setItem(KEY, JSON.stringify(data));   // ② 로컬에 쓰기
window.dispatchEvent(new CustomEvent("spum:studio-storage-write",{detail:{key:KEY}}));
window.spumStudioData.saveServerSnapshot("manual");// ③ 서버로 올리기
// ④ 페이지 새로고침해야 앱이 읽는다
```
> ❌ **서버에 직접 `PUT /api/studio/state` 하지 말 것.** 다음 새로고침 때 브라우저 로컬이 서버를 덮어써서 작업이 사라진다. (팀원이 3번 당함)

**A-2. 캐스트 "배치"만은 코드 금지**
`world.casts[]`에 항목을 코드로 만들면 앱이 *"없는/중복 캐릭터 배치 N개를 정리했습니다"* 로 **전부 삭제**한다. → World Editor 좌측 `Characters`의 **`+` → "배치"** 버튼으로. 한 명씩 누르고 확인(연속 클릭은 리렌더로 씹힘).
※ 캐릭터 **생성·수정·삭제**, **외형·색상**, **맵 레이어**, **월드의 mapId 교체**는 코드로 잘 된다.

**A-3. 세션은 30분 안팎으로 만료된다 → 자동 복구**
`/api/me`가 `{"user":null}`이면 만료. 우측 상단 `SSAM … 로그인 필요` 배지 → ACCOUNT 패널 → **「다시 로그인」** → 4초. **비밀번호 안 물어봄**(SSO 살아있으면). 복구 후 `saveServerSnapshot("manual")`로 재동기화.

**A-4. Cast Export(스프라이트 시트)는 신뢰하지 말 것**
Generate가 비동기라 **직전 캐릭터의 시트가 다운로드된다.** 미리보기로 눈 확인까지 해도 어긋났다. 받은 뒤 반드시 JSON의 `characterName`으로 검증할 것. (5명 중 2명만 정상 확보됨)

**A-5. 썸네일은 코드로 외형을 바꿔도 갱신 안 된다**
`localStorage` 패치로 `appearance`를 바꿔도 `sv_studio_thumb_*`는 예전 이미지 그대로. 목록/추출물이 쌍둥이로 보이면 이것 때문.

**A-6. 타일셋 셀 크기는 이미지에서 계산할 것**
`mapTheme.grid`가 `"16x16"`이어도 셀이 64px이라는 뜻이 아니다. **셀 = 이미지폭 ÷ 16**. 실제로 192×192 이미지라 **셀 12px**이었고, 64로 착각해 한참 헤맸다.

## B. 브라우저 자동화

**B-1. 네트워크/DOM 덤프로 base64를 뽑지 말 것**
`read_network_requests`로 이미지 요청을 조회하면 **base64가 통째로 쏟아져 컨텍스트가 순식간에 고갈된다.** 반드시 필터링해서 개수·상태코드만 볼 것.

**B-2. `javascript_tool` 반환값이 차단될 때가 있다**
쿠키/쿼리스트링/대용량이 섞이면 `[BLOCKED]`. → **`document.title`에 값을 써서 탭 제목으로 읽는 우회가 잘 통한다.**

**B-3. iframe 안을 봐야 할 때가 있다**
Object Tile Editor는 `/studio/pixeldeidtor/index.html` iframe. 부모 document 쿼리로는 아무것도 안 잡힌다. → `document.querySelector('iframe[src*="pixeldeidtor"]').contentDocument`

**B-4. 커스텀 드롭다운은 화면 클릭으로 안 열린다**
네이티브 `<select>`가 아니면 스크린샷에 팝업이 안 뜬다. iframe 내부 `<select>`를 찾아 `value` 설정 후 `input`/`change` 이벤트를 dispatch.

**B-5. 프리셋을 바꾸면 프롬프트가 덮어써진다**
Object Editor에서 Preset 변경 시 Reference Prompt가 프리셋 기본값으로 리셋된다. **프리셋 먼저 → 프롬프트 나중.**

## G. 이번 세션에서 실제로 틀렸던 것 (재발 방지)

1. **기획 오독** — 플레이어를 "외부 탐정"으로 구현했으나, 실제로는 **거주자 중 한 명**. UI를 다 만든 뒤에 발견했다. → **만들기 전에 "플레이어는 누구인가"부터 확인한다.**

4. **도구 파헤치기에 시간 과다** — MCP 연결에 오래 매달렸으나 결국 게임과 무관했다. → **결과물에서 멀어지면 즉시 중단하고 보고한다.**

## H. 맵 데이터 (2026-08-19 레이어 재구성에서 얻음)

**H-1. 시각 레이어와 통행(obstacle)을 같은 함수에서 쓰지 말 것.**
한 함수가 둘 다 건드리면 **러그가 벽이 된다.** 그림을 어디에 얹을지와 걸어갈 수 있는지는
별개 판단이다. 우리 `stamp()` 는 그림만 얹고, 통행은 마스크 문자로만 정한다.

**H-2. 손으로 찍은 좌표엔 반드시 walkable 검사를 붙일 것.**
같은 실수를 두 번 했다 — 맵 생성기(가구가 문을 봉인)에서 한 번, NPC 소집 지점(모임 지점이
라운지 가구 위)에서 또 한 번. 눈으로는 절대 안 보인다.

**H-3. 스탬프가 벽 위에 걸치는 칸을 조심할 것.**
예전 코드는 마스크의 `.` 칸에 `obstacle = 0` 을 **강제로** 써서 벽에 구멍을 뚫고 있었다.
지금은 뚫지 않고, "밟을 수 없으면 러그가 아니다" 규칙으로 가구로 강등한다.
**강등 건수를 로그로 찍는다** — 조용히 넘어가면 다음 사람이 모른다.

**H-4. 휑한 정도는 눈이 아니라 숫자로 본다.**
`build-map.mjs` 가 **맨바닥 비율**과 **구역별 가구 점유율**을 찍는다.
현재 맨바닥 91% — 이게 "휑하다"의 정체다. 개선하면 이 숫자가 내려가야 한다.

**H-5. 맵 스키마는 SPUM 과 같은 `layers[]` 배열로 둔다.**
객체(`{back_1:…, front_1:…}`)로 두면 **순서 정보가 없어** 다중 레이어를 표현할 수 없고,
Studio 로 밀어넣을 때 변환이 필요하다. 배열 순서가 곧 렌더 순서다.

**H-6. 넓은 면에 깔 타일은 눈으로 고르지 말고 `tools/tile-report.mjs` 로 고를 것.**
타일 173장을 사람이 일일이 보는 건 비현실적이다. 도구가 픽셀에서 3가지를 계산한다:
`flat`(내부 색 분산) · `tileH`/`tileV`(좌↔우, 상↔하 가장자리 일치도). 점수가 낮을수록 안전.

```bash
node tools/tile-report.mjs        # 상위 후보 + 현재 맵이 쓰는 타일의 순위
```

현재 바닥으로 쓰는 `2280` 은 **10위/256** 이었다(선택이 맞았다는 확인).
반대로 부엌 체크무늬 `2092` 는 190위 — 넓게 깔면 무늬가 튄다.

**H-7. ⛔ 이 시트로는 러그·카펫을 넓게 깔 수 없다 (측정으로 확인).**
점수 40 이하(넓은 면에 안전)인 타일이 **256장 중 6장뿐이고 전부 갈색 원목 계열**이다.
**비-갈색 계열은 0장** — 최고점이 123.6 으로 안전 기준의 3배다.
러그 타일 29종은 전부 4칸씩 흩어져 있고 순위도 68~222위 — **가구와 한 덩어리로 그려져 있어
떼어낼 수 없다.**

→ **맨바닥 비율을 낮추려면 새 타일이 필요하다.** 기존 시트 재배치로는 안 된다.
   필요한 것: ① 평평하고 사방으로 이어지는 **러그/카펫** ② `front_1` 용 **덮개 조각**(문틀 상인방 등).
   둘 다 Object Editor 작업이다.

**H-8. 이미지 모델에 `seamless` 를 요구하지 말 것. "평평한 단색 면"을 요구할 것.**
AI 타일 생성 1차에서 "MOSTLY seamless … edge-matching" 이라고 썼더니 안전 타일이 **0장**
나왔다. 2차에서 "**PLAIN FLAT COLOR FIELD**, no borders, no objects, almost uniform" 로
바꾸고 품질을 올렸더니 **최고점 27.6**(기존 시트 최고 32.7보다 좋음)이 나왔다.
**균일한 칸은 좌우·상하 가장자리가 자동으로 일치한다** — 이어붙임은 결과지 목표가 아니다.

**H-9. 점수 임계선은 40이 아니라 ~50이다.**
현재 803칸에 깔려 있는 바닥 `2280` 이 **43점**인데 멀쩡하다. "안전 ≤40" 은 처음에 임의로
잡은 선이었다. 실무 임계는 **50 안팎**으로 보고, 그 이상은 눈으로 확인할 것.

**H-10. 레이어 하나에 타일셋을 섞지 말 것 — 조용히 사라진다.**
러그를 얹으면서 실제로 냈다. `back_2` 에 스탬프에서 나온 본 테마 ID(2049~) 28칸과
AI 러그 ID(4097~) 187칸이 **섞여 있었다.** 렌더러는 레이어당 `TileSet` 이 하나뿐이라
범위 밖 ID 는 **에러 없이 안 그려진다** — 픽셀 검사도 통과해 버렸다(러그가 다수라).

→ 레이어를 갈랐다(`back_2` 스탬프 러그 = main / `back_3` AI 러그 = rug).
→ **빌드 검증기를 붙였다.** 레이어의 모든 ID 가 그 레이어 타일셋의 범위
   `[tileIdBase, tileIdBase+256)` 안에 있어야 하고, 아니면 빌드가 실패한다.

> 교훈: **"화면에 보이니 됐다"는 검증이 아니다.** 다수 타일이 정상이면 소수의
> 사라진 타일은 픽셀 비율로 안 잡힌다. 데이터 불변식을 직접 검사해야 한다.

**H-11. 지표에 과최적화하지 말 것 — 눈으로 볼 방법을 먼저 확보하라.**
"맨바닥 91%" 를 낮추려고 방 내부를 통째로 러그로 덮었더니 **카펫이 아니라 잔디밭**이 됐다.
숫자는 71% 로 좋아졌지만 화면은 나빠졌다. 러그는 "공간을 구분하는 점"이지 바닥재가 아니다.
→ 면적을 줄이고 톤을 통일(남색)하니 맨바닥은 86% 로 올라갔지만 **화면은 훨씬 낫다.**

**H-12. 게임 화면은 실제 크롬(`claude-in-chrome`)으로 직접 본다.**
앱 내장 브라우저는 창이 표시되지 않으면 스크린샷이 실패한다("Browser pane is not displayed").
**실제 크롬으로 `localhost:5173` 을 열면 그냥 보인다.** 이걸 몰라서 한동안 주영님께
"직접 봐 달라"고 떠넘겼다. 픽셀 비율 검사는 보조 수단이지 육안 확인의 대체가 아니다.

## I. SPUM Studio 저장 (2026-08-19 · 작업을 두 번 날리고 얻음)

**I-1. 저장은 세 가지가 동시에 성립해야 된다 — 하나라도 깨지면 조용히 실패한다.**
① 로그인(`/api/me` 에 user) ② `localStorage` 여유(약 5MB 한도) ③ 동기화 상태 정상.
어느 것이 깨졌는지 **앱은 알려주지 않는다.** `saveServerSnapshot()` 이 그냥 `false` 다.

**I-2. 무거운 작업(생성·Slice) 전에 용량부터 잰다.**
```js
let u = 0; for (const k of Object.keys(localStorage)) u += localStorage.getItem(k).length;
console.log((u/1048576).toFixed(2) + 'MB / 약 4.98MB');
```
32×32 테마 하나가 0.4MB 다. 여유가 0.5MB 미만이면 **만들기 전에 정리**한다.

**I-3. 만들었으면 그 자리에서 저장을 확인한다.**
`saveServerSnapshot()` 의 반환값이 `true` 인지, `spum_studio_server_sync_v1.revision` 이
올라갔는지 **둘 다** 본다. 나중에 확인하면 이미 늦다 — 새로고침이 서버 상태로 되돌린다.

**I-4. 진단 순서 (저장이 false 일 때)**
```js
await fetch('/api/me').then(r=>r.json())            // ① 로그인
// ② 용량 (위 I-2)
JSON.parse(localStorage.spum_studio_server_sync_v1) // ③ revision 이 멈춰 있나
// ④ fetch 를 가로채 요청이 실제로 나가는지 확인 — 안 나가면 클라이언트 사전 검사에서 막힌 것
```
**요청이 안 나가면 서버 문제가 아니다.** 로그인·용량·동기화 셋 중 하나다.

**I-5. 원인을 못 찾으면 거기서 멈추고 보고한다.**
실제로 위 셋이 다 정상인데도 저장이 안 되는 상태를 만났다(revision 110 고정).
재로그인·새로고침·용량 확보 모두 시도했으나 해소되지 않았다.
**추측으로 밀어붙이지 말 것** — 로컬 작업은 레포에 커밋해 두고, 제품 이슈로 기록한다
(`docs/spum-feedback.md` A-2).

## J. refs 클릭과 슬라이스 기준 (2026-08-19 · 해커톤 세션 5차)

**J-1. ⚠ refs 썸네일을 "구경"만 해도 테마의 슬라이스 기준이 바뀐다 ★★★★☆**

Object Editor 좌하단 refs 스트립에서 카드를 클릭하면 상태바에 `Reference opened in
Preview canvas` 가 뜬다. **미리보기일 뿐이라고 생각했는데 아니었다.**

증거(백업 2개 대조):

| 시점 | 테마 `sliceBaseAssetId` |
|---|---|
| 17:07 백업 (클릭 전) | `""` (비어 있음) |
| 클릭: refs 3번(= v2 그림) | |
| 18:16 백업 (클릭 후) | `sha256:bdbc02f3…` = **v2** |

그 사이에 한 일은 **refs 3번 클릭 하나뿐**이다. Slice 버튼은 누르지 않았다.

→ **refs 는 읽기 전용이 아니다.** 어떤 그림이 들어왔는지 확인할 목적이라도
클릭하기 전에 현재 `sliceBaseAssetId` 를 적어 두고, 끝나면 되돌릴 것.

```js
// 클릭 전에 반드시
JSON.parse(localStorage.sv_studio_smo_v1).find(t => t.id === "SMO_...").mapTheme.sliceBaseAssetId
```

**J-2. 문서의 "적용돼 있다"를 믿지 말고 해시를 직접 읽을 것 ★★★★★**

`handoff.md` 는 "v5 가 Studio 에 적용돼 있다(해시 64자리 일치 확인)"고 적혀 있었으나,
지금 실제로 읽으면 **어느 테마도 v5 를 기준으로 쓰고 있지 않다.**
재부팅 후 백업 복원이 되돌렸거나(가능성 높음), 그 사이 다른 조작이 덮었다.

→ **"적용 완료" 기록은 시점 정보다. 작업 시작 전에 매번 다시 읽는다.**
읽는 법은 J-1 의 한 줄.

**J-3. 테마 소스 삭제는 IndexedDB 확인 후에 하면 안전하다 ★★★★★**

`localStorage` 의 `spum-map-theme-source-state:*` 를 지워도 **원본은
