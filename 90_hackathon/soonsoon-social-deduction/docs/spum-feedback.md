# 순순팩토리에 전달할 제품 피드백

> 「누가 내 케이크 먹었어?」를 만들며 **실제로 부딪힌 것만** 적었다. 추측은 신뢰도로 표시한다.
> ★★★★★ 직접 확인 / ★★★★☆ 문서 근거 / ★★★☆☆ 추정 / ★★☆☆☆ 불확실
>
> 목적: 비난이 아니라 **레퍼런스 데모를 만들며 나온 사용자 관점 리포트**다.
> 과제정의서 §4가 "제품 쇼케이스"를 목적으로 밝혔으므로, 그 과정의 마찰도 산출물의 일부로 본다.

## A. 저장·동기화 (가장 아픈 것)

### A-1. `localStorage` 5MB 한도에 금방 닿는다 ★★★★★

Studio 는 작업 데이터를 브라우저 `localStorage` 에 먼저 쓰고 서버로 올린다. 그런데
**`localStorage` 는 브라우저 표준상 오리진당 약 5MB** 다. 실측:

```
현재 사용            4.86 MB
추가로 쓸 수 있던 양   0.13 MB
한도 (실측)          4.98 MB   → QuotaExceededError
브라우저 전체 저장소   10,349 MB 중 109 MB 사용   ← 디스크는 남아돈다
SPUM 계정 서버 용량    931 MB 남음               ← 서버도 남아돈다
```

**32×32 격자 테마 하나가 약 0.4MB** 다(1024×1024 원본 + 슬라이스 상태). 기본 제공
`SMO_BUILTIN_STONE_WALL` 의 소스 상태만 **2.67MB** 로 절반 이상을 차지한다.
→ **테마 두세 개만 만들면 한도에 닿아 아무것도 저장되지 않는다.**

> ⚠ 위 수치는 **문자 수 기준**이다(A-5). 바이트로는 약 2배다.
>
> ⚠ **원인은 A-4 에서 밝혀졌다** — IndexedDB 이전은 이미 돼 있고, localStorage 사본이 문제다.
>
> 제안: 큰 이미지 상태는 `IndexedDB` 로 옮기면 한도가 수백 MB~GB 로 올라간다.
> 최소한 **한도 근접 경고**와 **테마별 용량 표시**가 있으면 사용자가 대응할 수 있다.

### A-2. 저장 실패가 조용하다 — 원인을 알 수 없다 ★★★★★

`spumStudioData.saveServerSnapshot('manual')` 이 실패할 때:

- **HTTP 요청이 아예 나가지 않는다** (`fetch` 를 가로채 확인 — 요청 0건)
- **콘솔에 아무것도 안 찍힌다** (`console.log/warn/error/info/debug` 전부 후킹 — 0건)
- 예외도 안 던진다. 그냥 `false` 를 반환한다
- UI 토스트는 `"확인 실패"` · `"수동 서버 스냅샷을 저장하지 못했습니다. 서버 연결 또는
  동기화 충돌 상태를 확인해주세요."` — **어느 쪽인지 구분이 안 된다**

로그인 정상(`/api/me` → user 있음), 용량 0.83MB 여유, 재로그인·새로고침 모두 시도해도
`spum_studio_server_sync_v1.revision` 이 110에서 움직이지 않았다.
**사용자가 스스로 복구할 방법이 없다.**

> ✅ **원인 규명 완료 → A-6.** 클라이언트 교착이었고, 우회로로 실제 해결했다.

> 제안: 실패 사유를 코드로 구분해 반환하고(`quota` / `conflict` / `auth` / `network`),
> 토스트에 그 사유와 다음 행동을 적어 줄 것.

### A-3. 로그인 만료 시 작업이 조용히 사라진다 ★★★★★

세션이 30분쯤에 만료된다. 만료 상태에서도 **에디터는 정상 동작하고 생성도 된다.**
그런데 서버 저장이 멈추고, **새로고침하면 서버 상태가 로컬을 덮어써 그동안의 작업이 사라진다.**

실제 피해: 32×32 평면도 테마 1개 + 맵 레이어 6장 재구성이 통째로 날아갔다.
배너에 "서버 백업 중지" 안내는 뜨지만 **작업을 막지는 않는다.**

> 제안: 만료 시 저장이 필요한 동작(생성·Slice)을 **차단하거나**, 최소한 모달로 가로막을 것.
> 또는 만료 직전 자동 갱신.

### A-4. 같은 데이터를 IndexedDB 와 localStorage 에 **둘 다** 쓴다 ★★★★★

A-1 을 조사하다 원인을 찾았다. **큰 이미지를 IndexedDB 로 옮기라는 제안은 이미 구현돼 있다.**
그런데 같은 것을 `localStorage` 에도 쓰고 있고, 한도를 때리는 쪽은 그 사본이다.

키 이름이 글자 하나까지 같다 — `spum-map-theme-source-state:{SMO_ID}`

| 테마 | localStorage | IndexedDB `spum-map-theme-source-library` |
|---|---|---|
| Custom SMO 4 (32x32) | 1.66MB | **23.76MB** |
| 셰어하우스 인테리어 | 4.59MB | **6.01MB** |
| Custom SMO 1 | 없음 | 11.65MB |
| Custom SMO 3 | 없음 | 8.71MB |
| 기본 맵 데이터 | 없음 | 5.53MB |
| **합계** | **6.25MB** | **55.66MB** |

- IndexedDB 에는 테마 **5개 전부**가 온전히 들어 있다. 브라우저 전체 한도는 10,355MB 로 여유롭다
- `localStorage` 에는 **최근에 만진 2개만** 있다 → 성능용 캐시로 보인다 [추정]
- 그 캐시 2개가 전체 `localStorage` 의 **65%** 를 차지하고, 한도(5,239,745자)의 96% 를 채운다

**즉 저장소 설계는 이미 옳고, 캐시 계층만 한도가 없는 곳에서 있는 곳으로 잘못 내려가 있다.**

> 제안: `localStorage` 쪽 `spum-map-theme-source-state:*` 쓰기를 제거하거나,
> 캐시가 필요하면 **메모리** 또는 IndexedDB 로 옮길 것. 데이터 이전(migration)이 필요 없다 —
> 원본이 이미 IndexedDB 에 있으므로 **쓰기 한 줄을 빼는 것으로 끝난다.**
>
> 이 한 줄이 A-1(한도 초과) · A-2(조용한 저장 실패) · A-3(작업 소실)의 공통 뿌리다.

### A-5. 한도 표기가 문자 수인지 바이트인지 모호하다 ★★★★☆

실측 한도는 **5,239,745자**다. `localStorage` 는 UTF-16 이라 바이트로는 **약 10MB** 다.
"5MB 한도"라고 부르면 절반으로 오해한다. 우리도 세션 중 이 단위 때문에 두 번 혼동했다.

> 제안: 용량 UI 를 만들 때 **문자 수와 바이트를 같이** 보여줄 것.

### A-6. 서버 상태가 유실되면 **영구히 저장 불가 상태에 갇힌다** (교착) ★★★★★

A-2 의 "조용한 저장 실패"의 진짜 원인이다. **버그를 특정하고, 재현하고, 우회로 해결까지 확인했다.**

**교착 구조 — 쓰기를 켜려면 읽기가 성공해야 한다**

```js
async function _initServerStudioSync() {
  try { payload = await _fetchServerStudioState(); }   // GET /api/studio/state
  catch (error) { log('warn', ...); return; }          // ← 500 이면 여기서 나간다
  ...
  _serverSync.enabled = true;                          // ← 도달 불가
}

async function _saveStudioStateToServer(reason) {
  if (!_serverSync.enabled || _serverSync.conflict || _serverSync.saving) return false;   // ← 즉시 차단
```

S3 에서 상태 오브젝트가 사라지면:

1. `GET /api/studio/state` → 500 `studio_state_object_missing`
2. `_initServerStudioSync()` 가 조기 return → `_serverSync.enabled` 가 false 로 남는다
3. 모든 저장 시도가 첫 줄에서 차단 → **HTTP 요청 0건 · 콘솔 0건 · 예외 없음 · `false` 반환**
4. 재로그인해도 `_initServerStudioSync()` 를 다시 부를 뿐이라 **같은 자리**

**읽을 것이 없으면 새로 쓸 수도 없다.** 사용자에게 복구 수단이 없다.

**증상 확인 (로그인 정상 상태에서)**

| 엔드포인트 | 응답 |
|---|---|
| `GET /api/me` | 200 · user 정상 |
| `GET /api/studio/revisions` | 200 · 리비전 20건 메타데이터 **정상** |
| `GET /api/studio/state?revision=110` | 500 `studio_state_object_missing` |
| `GET /api/studio/state?revision=91` | 500 (**가장 오래된 것도 동일**) |
| `GET /api/studio/storage` | 500 (용량 계산에 상태 객체를 읽는다) |

DB 의 리비전 원장(해시·크기·시각)은 20건 전부 온전한데 **S3 오브젝트만 전부 없다.**
즉 원장과 오브젝트 스토리지가 어긋난 상태이고, 클라이언트는 이를 복구할 수 없다.

**해결 확인 ★★★★★**

`GET /api/studio/state` 응답만 일시적으로 "빈 상태(`keys:{}`)"로 만들어 주면,
클라이언트가 스스로 아래 분기를 타고 로컬을 서버로 올린다.

```js
if (!serverHasData && localHasData) { await _saveStudioStateToServer('initial'); return; }
```

결과: `PUT /api/studio/state` → **200 · revision 111 생성.** 이후 `GET` 도 200 으로 돌아왔고,
용량 배지도 "확인 실패" → "911 MB left" 로 정상화됐다. **서버 쓰기 경로는 처음부터 멀쩡했다.**

> **제안 (난이도 순)**
> 1. `_initServerStudioSync()` 에서 상태 읽기가 **500** 일 때, 빈 상태로 간주하고
>    `enabled = true` 로 진행할 것. 로컬 데이터가 있으면 그것을 새 리비전으로 올리면 된다.
>    (401/404 는 이미 `null` 을 반환해 이 경로를 타므로, **500 만 예외 취급되고 있다.**)
> 2. 서버: 원장에 리비전이 있는데 오브젝트가 없으면 그 리비전을 무효로 표시하고
>    빈 상태를 반환할 것. 500 은 클라이언트가 복구할 수 없는 응답이다.
> 3. 저장 실패 토스트에 사유를 구분해 표시할 것 (A-2 제안과 동일).

## B. 에디터 ↔ 엔진 사이의 끊긴 길

### B-1. Cast Editor 가 뽑은 시트를 엔진이 재생하지 못한다 ★★★★★

Cast Editor 는 `{이름}_idle.png/.json` 을 내보낸다(128px · 8×2 · 15프레임 · 30fps · 투명).
그런데 엔진에 **그 시트를 재생할 컴포넌트가 없다.**

- `Animator` 는 **스켈레톤 파트** 애니메이터다(쿼터니언·파트 경로). 슬롯 파츠 JSON 을 요구한다
- `SpriteRenderer`/`ImageRenderer` 는 `drawImage` 를 4인자로만 호출한다 —
  **이미지 일부만 잘라 그리는 기능이 없다**

즉 추출물을 다시 엔진에 넣는 경로가 비어 있다. 우리는 `SheetAnimator` 를 직접 만들었다(약 60줄).

> 제안: 시트 재생 컴포넌트를 엔진에 넣거나, 최소한 예제 코드를 문서에 실을 것.

### B-2. `BubbleRenderer` 가 루트 `index.js` 에서 export 되지 않는다 ★★★★★

UI 3종 중 `FloatingTextRenderer`·`ProgressBarRenderer` 만 루트에 있다.
`BubbleRenderer` 는 `lib/domain/ui/index.js` 로 직접 들어가야 한다. 단순 누락으로 보인다.

### B-3. `PathfindingManager.buildFromTileMap()` 이 Object Editor 산출 테마와 안 맞는다 ★★★★★

내부에서 **타일 속성 `walkable`** 을 읽는데, Object Editor 로 만든 테마에는 그 속성이 없어
전부 통행 가능으로 나온다. 우리는 맵의 `obstacle` 레이어를 `setGrid()` 로 직접 넘겨 우회했다.

### B-4. `TileMapSystem` 은 타일셋이 단수, `TileMapRenderer` 는 sortingLayer 가 하나 ★★★★★

- 레이어마다 다른 시트를 쓰면 **타일맵 GameObject 를 따로** 만들어야 한다
- 캐릭터를 레이어 사이에 끼우려면(앞/뒤 덮개) 역시 따로 만들어야 한다

맵 데이터는 `back_1 / back_2 / front_1` 처럼 **캐릭터 기준 앞뒤 레이어를 이미 표현**하는데,
렌더러가 그걸 한 번에 못 그린다. 데이터 모델과 렌더러가 어긋나 있다.

### B-5. 엔진에 시야/안개 시스템이 없다 ★★★★★

`fog`·`vision`·`sight`·`occlusion` 전수 검색 결과 없음.
다만 **SMO 스키마에는 `collision.blocksVision` 필드가 있다** — 데이터는 준비돼 있고 런타임이 없다.

## C. AI 생성 관련

### C-1. 이미지 모델은 "seamless" 같은 추상 지시를 못 따른다 ★★★★★

타일 생성 1차: `"MOSTLY seamless … edge-matching"` → 넓은 면에 쓸 수 있는 타일 **0장**.
2차: `"PLAIN FLAT COLOR FIELD, no borders, no objects, almost uniform"` + 품질 `high`
→ 안전 타일 **2장**, 최고 점수 **27.6** (기존 테마 최고 32.7보다 좋음).

**"평평한 단색 면"을 요구하면 이어붙임은 저절로 따라온다.** 균일한 칸은 가장자리가 자동으로 맞는다.
부수 효과로 자동 분류도 정확해졌다(1차 `obstacle_slowing` 32개 → 2차 `floor` 53개·전부 `passable`).

> 제안: Object Editor 프롬프트 입력란에 이 팁을 예시로 넣으면 첫 사용자의 실패가 크게 준다.

### C-2. 32×32 격자로 "평면도"를 생성하면 결과가 확 좋아진다 ★★★★★

16×16 격자로 "타일 모음"을 만들어 조각내 재조립하면, 원본의 밀도와 벽 구조가 버려진다.
**격자를 32×32 로 올리고 "위에서 본 평면도"를 요구**하면 두꺼운 벽·방별 색 러그·비대칭
배치가 통째로 나온다. 1024×1024 / 셀 32px 이라 게임 타일 크기와 1:1 이다.

> 이건 결함이 아니라 **잘 안 알려진 사용법**이다. 문서나 프리셋으로 안내하면 좋겠다.

### C-3. 생성 결과에 통행 정보가 없다 ★★★★☆

평면도는 그림이라 어디를 걸을 수 있는지 알 수 없다. Classify 가 리소스를 분류해 주지만
32×32 평면도는 **1024셀 중 887~925개가 고유 리소스**라 분류 대상이 지나치게 많다.
우리는 셀별 **국소 대비(색 분산)** 로 판정했다 — 바닥은 균일하고 가구·벽은 윤곽선이 있어 갈린다.
